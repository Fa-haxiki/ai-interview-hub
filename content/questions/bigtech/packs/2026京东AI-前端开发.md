### 简单介绍一下浏览器的事件循环机制。

事件循环是 JavaScript 处理异步任务的核心机制，通过任务队列协调主线程执行栈与异步回调。

- 宏任务：包括script 全体代码、setTimeout、setInterval、I/O。

- 微任务：包括 Promise.then、MutationObserver、process.nextTick。

- 执行顺序：先执行同步代码，清空微任务队列，再取出一个宏任务执行，循环往复。

- 渲染时机：浏览器通常在微任务队列清空后、下一个宏任务开始前尝试进行 UI 渲染。常见坑：

- 误认为Promise构造函数内部是异步的。

- 忽略了 await 后面的代码会被包装成微任务。

### Promise 有哪几种状态？如何实现 Promise.all?

Promise 有 Pending、Fulfilled、Rejected 三种状态，状态一旦改变不可逆转。

- Promise.all 接收一个 Promise 数组，返回一个新的 Promise。

- 成功条件：所有成员都成功，返回结果数组。

- 失败条件：只要有一个成员失败，立即返回该失败原因。

- 计数器：内部需维护一个计数器，确保所有异步操作完成后再 resolve。

- 忘记处理非 Promise 类型的输入元素。

- 计数器逻辑错误导致提前返回。

追问：

- 如果想让所有 Promise 都执行完（无论成功失败）再返回，该用哪个 API?

1 function promiseAll(promises) {
2    return new Promise((resolve, reject) => {
3    let result = [];
4    let count = 0;
5    promises.forEach((p, index) => {

11    });
12    });

### 在 AI 聊天场景中，SSE 和 WebSocket 有什么区别？

SSE 是基于 HTTP 的单向流式传输，而 WebSocket 是全双工的二进制协议。

- 方向性：SSE 仅支持服务端向客户端推送；WebSocket 支持双向通信。

- 协议开销：SSE基于标准HTTP，更轻量，支持自动重连；WebSocket需握手升级，协议较重。

- 场景匹配：AI问答多为一问一答，服务端持续输出，SSE非常适合这种单向流。

- 兼容性：SSE在HTTP/2下性能极佳，且能穿透大多数防火墙。常见坑：

- 认为 SSE 只能传输文本，其实可以通过 Base64 传二进制。

- 忽略了 HTTP/1.1 下 SSE 有最大连接数限制。

### 谈谈 CSS 中的 Flex 布局和 Grid 布局的应用场景。

Flex 是一维布局，侧重于轴线上的对齐；Grid 是二维布局，侧重于行列网格的划分。

- Flex 场景：导航栏对齐、列表项排列、垂直居中。

- Grid场景：复杂的仪表盘界面、响应式多列布局、整体页面骨架。

- 性能：Flex 渲染效率略高，Grid 在处理复杂嵌套时能减少 DOM 层级。

- 混淆 flex-grow 和 flex-shrink 的计算逻辑。

- 在 Grid 中过度使用绝对定位导致布局塌陷。

### 什么是 Token？在前端处理 AI 接口时为什么要关注 Token 长度？

Token 是模型处理文本的最小单位，通常一个单词或汉字会被切分为一个或多个 Token。

- 成本控制：大模型 API 通常按 Token 计费。

- 上下文限制：模型有 Context Window 限制，超过长度会导致丢失记忆。

- 性能影响：Token 越多，推理时间越长，前端需要做截断或摘要处理。

- 简单地用字符长度（length）等同于 Token 数量。

### 手写一个深拷贝函数，考虑循环引用。

深拷贝需要递归遍历对象属性，并处理特殊类型及循环引用问题。

- 基本实现：递归处理对象和数组。

- 循环引用：使用WeakMap存储已拷贝的对象。

- 特殊类型：考虑 Date、RegExp、Set、Map 等类型的克隆。

常见坑：

- 使用 JSON.parse(JSON.stringify()) 丢失函数和正则。

- 递归层级过深导致栈溢出。

追问：

- 为什么使用 WeakMap 而不是 Map?

```javascript
function deepClone(obj, map = new WeakMap()) {
    if (obj === null || typeof obj != 'object') return obj;
    if (map.has(obj)) return map.get(obj);
    let target = Array.isArray(obj) ? [] : {};
    map.set(obj, target);
    for (let key in obj) {
    if (obj.hasOwnProperty(key)) {
    target[key] = deepClone(obj[key], map);
    }
    }
    return target;
}
```

### React 的 Fiber 架构解决了什么问题？它的工作原理是什么？

Fiber 解决了 React 在处理大量 DOM 更新时主线程阻塞导致的卡顿问题。

- 核心思想：将渲染过程拆分为可中断的微任务（Work Loop）。

- 优先级调度：通过 Scheduler 调度不同优先级的任务，保证动画等高优先级任务先执行。

- 双缓存技术：在内存中构建 WorkInProgress Tree，完成后一次性提交到真实 DOM。

- 协调过程：从递归同步更新转变为循环异步更新。

常见坑：

- 误认为Fiber提高了渲染的绝对速度，实际上它提高的是交互响应性。追问：

- 哪些生命周期在 Fiber 架构下被废弃了？为什么？

### AI 聊天界面的流式文本渲染，前端如何优化性能以防止页面卡顿？

流式渲染面临高频DOM更新和长列表渲染压力，需从更新频率和渲染范围入手。

- 节流更新：不要每收到一个字符就 setState，可以累积一定字符或按帧（requestAnimationFrame）更新。

- 局部更新：仅对最后一个对话气泡进行增量渲染，避免触发整个列表的Diff。

- 虚拟列表：当对话历史过长时，使用虚拟列表技术只渲染可视区域内的消息。

- 样式优化：对文本容器使用 contain: content 属性，减少重排范围。常见坑：

- 频繁触发滚动到底部的逻辑导致 CPU 占用过高。

- Markdown 解析器在流式输入时反复解析完整字符串。

### 如何设计一个通用的 Prompt 管理方案?

- 结构化定义：将 Prompt 分为 System、User、Assistant 等角色。

- 调试工具：在开发环境下提供预览功能，查看最终发送给模型的完整字符串。

- 直接在代码里硬编码长字符串，导致难以维护。

- 忽略了 Prompt 中的敏感信息过滤。

### Web Worker 在 AI 前端应用中有哪些使用场景？

Web Worker 用于将耗时计算从主线程剥离，保证 UI 响应。

- 向量计算：在前端进行简单的向量相似度计算（如本地搜索）。

- 数据转换：将后端返回的复杂流数据解析为 Markdown 或 JSON。常见坑：

### 谈谈 Vite 的预构建原理，为什么它比 Webpack 快？

Vite 利用了浏览器原生 ES Modules 和高性能工具（esbuild）。

- 开发环境：无需打包，按需加载，利用浏览器处理模块依赖。

- 预构建：使用 esbuild 将 CommonJS 依赖转为 ESM 并合并请求。

- 缓存策略：利用 HTTP 强缓存和文件系统缓存减少重复构建。

- 更新机制：基于HMR的局部热更新，不随项目规模变大而变慢。常见坑：

- 某些老旧库不支持 ESM 导致预构建失败。

### 如何评估一个 AI 前端组件库的质量？

AI 组件库除了常规指标，更需关注 AI 特有的交互规范。

- 响应性：对流式数据的处理是否平滑，是否有闪烁。

- 易用性：Prompt 接口是否简洁，是否易于集成到现有流程。

- 可访问性：AI生成内容是否符合A11y标准。

常见坑：

- 只关注视觉效果，忽略了复杂数据结构下的稳定性。
