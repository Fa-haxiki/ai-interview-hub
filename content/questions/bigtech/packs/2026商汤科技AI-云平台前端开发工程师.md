### 请简述一下 SSE（Server-Sent Events）与 WebSocket 的区别，为什么 AI 聊天场景多采用 SSE?

SSE是一种基于HTTP的单向推送技术，而WebSocket是全双工的二进制协议。在AI场景下，由于模型输出是单向流式的，SSE更加轻量且兼容性好。

- 协议层：SSE基于标准HTTP协议，WebSocket是独立的TCP协议

- 方向性：SSE仅支持服务端向客户端推送，WebSocket支持双向实时通信

- 断线重连：SSE 内置了自动重连机制，WebSocket 需要开发者手动实现

- 场景匹配：AI 文本生成是典型的单向长连接输出，SSE 握手简单，且能绕过部分防火墙限制

#### 常见坑：

- 忽略了浏览器对同一域名下SSE连接数限制（通常为6个）

- 没意识到 SSE 只支持文本格式，传输二进制需 Base64 编码

### Promise.all 和 Promise.allSettled 在处理多个 AI 模型接口并行调用时有什么区别？

Promise.all 具有原子性，任意一个请求失败则整体失败；而 Promise.allSettled 会等待所有请求结束并返回每个请求的状态。

- 成功机制：all 要求全部 resolve，allSettled 只要全部执行完即可

- 返回结果：all 返回结果数组，allSettled 返回包含 status 和 value/reason 的对象数组

- 容错性：在对比多个模型效果时，通常用 allSettled 以免单个模型超时导致整体无结果

- 性能：两者都是并行触发，不影响执行效率

#### 常见坑：

- 在Promise.all中没有对单个promise做catch，导致一个报错直接进入全局catch

- 混淆了 allSettled 的返回结构

### 手写一个防抖（Debounce）函数，并说明在 AI 搜索建议场景下的应用。

防抖是指在事件触发后延迟执行，若在延迟时间内再次触发则重新计时，用于减少高频请求。

- 核心逻辑：利用闭包存储 timer 变量，每次触发先 clearTimeout

- 绑定上下文：需正确处理 this 指向和 arguments 参数

- 立即执行：可选支持 leading 参数实现首次触发立即执行

- 场景应用：用户在AI搜索框输入时，等待停止输入后再请求后端接口

```javascript
1 function debounce(fn, delay) {
2    let timer = null;
3    return function(...args) {
4    if (timer) clearTimeout(timer);
5    timer = setTimeout(() => {
6    fn.apply(this, args);
7    }, delay);
8    }
9 }
```

#### 常见坑：

- 忘记清除旧定时器导致逻辑多次触发

- 箭头函数导致 this 指向错误

### 给定一个包含括号的字符串（如 AI 生成的代码块），判断其括号是否合法。

使用栈（Stack）数据结构，遍历字符串，遇左括号入栈，遇右括号判断栈顶是否匹配并出栈。

- 数据结构：使用数组模拟栈，push 入栈，pop 出栈

- 匹配逻辑：建立Map映射表存储括号对应关系

- 边界条件：遍历结束后栈必须为空，且中途不能出现栈空却有右括号的情况

- 复杂度：时间复杂度 $O(n)$ ，空间复杂度 $O(n)$

#### 常见坑：

- 忘记处理字符串中包含非括号字符的情况

- 逻辑判断顺序错误导致数组越界

### React 的 Fiber 架构是如何优化大模型流式输出时的 UI 渲染的？

Fiber 将渲染工作拆分为可中断的微任务，通过时间分片避免了长文本更新时阻塞主线程。

- 任务拆分：将虚拟DOM树转换为链表结构的Fiber树，支持增量渲染

- 优先级调度：流式输出的文本更新可以被标记为高优先级，确保打字机效果流畅

- 协调过程：双缓存技术（current 和 workInProgress）减少了 DOM 频繁操作的开销

- 并发模式：在渲染过程中，浏览器若有输入事件，Fiber可以暂停渲染优先响应用户

#### 常见坑：

- 误认为 Fiber 提高了计算速度，实际上它只是优化了调度

- 混淆了 Reconciliation（协调）和 Renderer（渲染）阶段

### 在处理 AI 返回的 Markdown 内容时，如何防止 XSS 攻击？

AI 生成的内容不可信，必须经过严格的过滤和转义。

- 解析阶段：使用成熟的库（如 marked, markdown-it）并开启安全配置

- 消毒处理：使用DOMPurify对生成的HTML进行清洗，剔除script、onerror等危险标签和属性

- 内容安全策略：配置 CSP 头部限制非法脚本执行

- 渲染限制：尽量使用 React/Vue 的默认插值，避免直接操作 innerHTML（除非经过消毒）

#### 常见坑：

- 认为AI不会生成恶意代码，从而直接渲染原始字符串

- 消毒库配置不当，误删了正常的数学公式或代码块样式

### 如何实现一个高性能的 AI 聊天长列表？

当对话达到成百上千条时，直接渲染会导致 DOM 节点过多，需采用虚拟列表（Virtual List）技术。

- 核心原理：只渲染可视区域内的DOM节点，通过padding或transform撑起总高度

- 动态高度：AI 回复长度不固定，需在渲染后通过 ResizeObserver 动态获取高度并更新偏移量

- 缓冲区：在可视区上下设置 buffer，避免快速滚动时白屏

- 节点复用：结合 React/Vue 的 key 属性，确保 DOM 节点的高效复用

#### 常见坑：

- 动态高度计算不准确导致滚动条跳动

- 滚动监听函数没有做节流处理

### AI 流式输出（Streaming）过程中，如果前端渲染跟不上后端推送速度，你会如何处理？

这本质上是一个生产者-消费者速率不匹配的问题，需要通过缓冲区和调度策略来解决。

- 缓冲区机制：建立一个前端队列存储收到的 chunk，不立即渲染

- 批量更新：利用 requestAnimationFrame 定时从队列中取出数据进行批量渲染，而非来一个渲染一个

- 策略降级：当堆积过多时，跳过中间态直接显示最新结果（丢帧处理）

- 任务切片：将复杂的 Markdown 解析过程放入 Web Worker 中执行

#### 常见坑：

- 每次收到 chunk 都触发 setState，导致高频 Re-render 引起页面卡死

- 忽略了内存占用，长时间堆积 chunk 导致 OOM

### 你们是如何监控 AI 云平台的性能指标的？

除了常规的FP/LCP，AI场景更关注首字响应时间（TTFT）和生成速率。

- 关键指标：TTFT（Time to First Token）、TPS（Tokens Per Second）、请求成功率

- 异常监控：监控 SSE 连接中断率、模型返回异常 JSON 的频率

- 性能埋点：记录从点击发送到看到第一行文字的完整耗时

- 链路追踪：前端生成 TraceID 传给后端，便于排查全链路延迟

#### 常见坑：

- 只监控 HTTP 状态码，忽略了业务逻辑上的“生成失败”

- 统计TPS时未剔除网络波动的影响
