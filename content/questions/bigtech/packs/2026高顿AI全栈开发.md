### 请简单介绍一下你对大模型流式输出（Streaming）在前端实现的理解。

流式输出通常利用 SSE 或 Fetch 的 ReadableStream 协议，实现模型生成内容时前端实时渲染，提升首字响应速度。

- 协议选择：SSE（Server-Sent Events）适用于单向文本流，Fetch 配合 ReadableStream 灵活性更高。

- 关键 API：使用 response.body.getReader() 异步迭代读取数据块。

- 文本解码：通过 TextDecoder 将二进制数据流转换为 UTF-8 字符串。

- 状态管理：需要处理流式拼接过程中的 UI 抖动和自动滚动逻辑。

常见坑：

- 忽略了 Fetch 对 HTTP/1.1 的连接数限制。

- 未处理流中断或网络异常导致的 JSON 解析失败。

### 在前端处理 AI 生成的长文本时，如何保证渲染性能？

#### 难度：★★

长文本渲染的核心在于减少DOM节点数量和控制重绘频率，避免随着对话增长导致页面卡顿。

- 虚拟滚动：对于历史对话记录，仅渲染可视区域内的消息组件。

- 节流渲染：在流式接收数据时，通过 requestAnimationFrame 限制 UI 更新频率。

- 增量解析：Markdown 解析器应支持增量模式，避免每次新字符进入都全量重新解析。

- 硬件加速：对长列表容器开启GPU加速，减少布局抖动。

常见坑：

- 每次收到字符都触发 React 状态更新导致整树重绘。

- 在流式过程中频繁计算DOM高度。

### 谈谈你在项目中是如何进行 Prompt 调试和管理的。

Prompt 应当作为一种代码资产进行版本化管理，并通过结构化模板提高输出的稳定性。

- 结构化设计：采用Role、Context、Task、Constraint的四段式结构。

- 变量注入：使用Mustache或自定义占位符动态拼接用户输入。

- 版本管理：将 Prompt 抽离为 JSON 或配置文件，不直接硬编码在业务逻辑中。

- 少样本提示：通过Few-Shot示例引导模型输出特定格式（如JSON）。常见坑：

- 直接在前端代码里拼接敏感 Prompt 导致泄露。

- 忽略了不同模型对同一 Prompt 的理解差异。

### 解释一下 TypeScript 中的泛型，并写一个处理 AI 接口返回值的泛型包装器。

泛型提供了类型参数化的能力，使得组件或函数可以复用于多种数据类型而不丢失类型检查。

- 定义：interface ApiResponse<T> { data: T; status: number; }。

- 约束：使用 extends 关键字限制泛型范围。

- 默认值：为泛型提供默认类型。

```typescript
1 interface ChatResponse<T = string> {
2    id: string;
3 choices: Array<{ message: { content: T } }>;
4 }
```

#### 常见坑：

- 滥用 any 导致泛型失去意义。

- 复杂嵌套下泛型推导失效。

### 详细聊聊 RAG（检索增强生成）在前端侧可以做哪些优化？

RAG结合了外部知识库和LLM，前端在其中主要负责数据预处理、引用来源展示和交互优化。

- 文档切片：在前端进行简单的文本清洗和分段，减少后端处理压力。

- 引用溯源：将模型输出中的引用标记（如[1]）与原始文档片段进行高亮关联。

- 本地索引：利用IndexedDB缓存已检索的向量数据，减少重复请求。

- 检索到的上下文过长导致超过模型 Token 限制。

- 引用来源展示不直观，用户无法验证准确性。

### React 的并发模式（Concurrent Mode）对 AI 对话场景有什么帮助？

并发模式允许 React 中断低优先级的渲染，保证 AI 流式输出时的用户输入和动画不卡顿。

- 优先级划分：将流式文本更新标记为低优先级（useTransition），保证输入框响应为高优先级。

- 渲染中断：当有新字符进入时，React 可以中断旧字符的渲染任务，直接处理最新状态。

- 减少掉帧：避免长对话列表更新时阻塞主线程。

常见坑：

- 错误地将所有状态都放入 transition 导致 UI 响应延迟。

- 忽略了并发模式下的闭包陷阱。

### 谈谈 AI 产品的 Token 计费策略在前端如何进行估算。

前端预估 Token 可以帮助用户控制成本，并防止请求超过模型限制。

- 算法实现：引入 js-tiktoken 或 gpt-tokenizer 库进行离线计算。

- 估算差异：中文和英文的 Token 计算逻辑不同，不能简单按字符数计算。

- 实时反馈：在输入框下方实时显示当前对话消耗的预估 Token。

- 截断策略：当接近 Context Window 限制时，提醒用户或自动总结历史记录。常见坑：

- 忽略了 System Prompt 和历史消息占用的 Token。

- 库文件体积过大影响首屏加载。

### 你们是如何处理 AI 生成内容中的安全问题的？

AI 可能会生成恶意脚本或违规内容，前端必须建立最后一道防线。

- 渲染安全：使用DOMPurify对模型生成的HTML/Markdown进行彻底消毒。

- 代码沙箱：如果 AI 生成了可执行代码，应在 iframe 或 Web Worker 中运行。

- 敏感词拦截：前端维护基础敏感词库，配合后端审核API进行双重校验。

- 提示词注入防护：对用户输入进行转义，防止破坏 Prompt 结构。

- 直接使用 dangerouslySetInnerHTML 渲染模型输出。

- 信任模型的输出，认为模型不会生成恶意代码。

### 复杂的 AI Agent 任务流中，如何管理长时任务的状态？

#### 难度：★★★

Agent任务通常包含多个子步骤，需要清晰的状态机管理来展示进度。

- 状态机设计：定义 idle, thinking, executing, verifying, success/fail 等状

- 进度追踪：通过 WebSocket 或长轮询获取后端 Agent 执行的每一步日志。

- 中断与恢复：支持用户手动中止任务，并能从持久化存储中恢复执行上下文。

- 局部更新：仅更新任务流中发生变化的节点，避免全局刷新。

- 状态逻辑散落在各个组件中，难以维护。

- 任务失败后的回滚逻辑缺失。

### 手写题：实现一个具有并发控制的请求调度器。

```javascript
class TaskQueue {
    constructor(max) {
    this.max = max;
    this.queue = [];
    this.running = 0;
    }
    add(task) {
    return new Promise((resolve, reject) => {
    this.queue.push({ task, resolve, reject });
    this.run();
    });
    }
    run() {
    while (this.running < this.max && this.queue.length) {
    const { task, resolve, reject } = this.queue.shift();
    this.running++;
    task().then(resolve).catch(reject).finally(() => {
    this.running--;
    this.run();
    });
    }
    }
}
```

### 如果让你设计一个企业级的 AI 全栈低代码平台，你会如何架构前端部分？

架构应关注组件协议化、逻辑抽象化以及与AI能力的深度集成。

- 协议驱动：定义一套标准的 JSON Schema 来描述 UI 组件与 AI 模型的绑定关系。

- 核心引擎：开发一个渲染引擎，负责解析 Schema 并处理 AI 触发的事件流。

- 插件化体系：将 Prompt 管理、知识库配置、模型选择抽象为独立微模块。

- 协同编辑：引入Yjs等CRDT库支持多人协同设计AI工作流。

- 监控链路：集成全链路 Trace，记录从用户输入到模型返回的每一个环节。常见坑：

- 过于绑定特定模型 API，导致切换模型时需要重构。

- 忽略了低代码平台的版本回滚和灰度发布能力。

### 谈谈 AI 全栈开发中，前后端职责边界应该如何划分？

#### 难度：★★

合理的边界划分能提高迭代效率并保障安全。

- 前端职责：负责交互体验、流式渲染、Prompt模板拼接、数据可视化、本地缓存。

- 后端职责：负责模型鉴权、Token计费统计、长时任务调度、向量数据库检索、敏感词过滤。

- 模糊地带处理：简单的 Prompt 逻辑可以放在前端提高响应，复杂的 Agent 编排必须放在后端。

- 协作协议：采用 Server-Sent Events 或 gRPC-Web 统一流式通信标准。常见坑：

- 前端直接调用模型 API 导致 Key 泄露。

- 后端返回数据格式过于复杂，导致前端解析逻辑过重。
