### 请简述一下浏览器的事件循环机制，特别是宏任务和微任务的区别。

事件循环是 JavaScript 处理异步操作的核心机制，通过任务队列的循环调度来保证单线程下的非阻塞运行。

- 宏任务（MacroTask）包括 script 全部代码、setTimeout、setInterval、I/O、UI 渲染。

- 微任务（MicroTask）包括 Promise.then、MutationObserver、process.nextTick。

- 执行顺序：执行一个宏任务 -> 清空当前微任务队列 -> 渲染页面 -> 下一个宏任务。

- 在AI问答流式输出场景中，微任务的及时处理决定了UI响应的流畅度。

- 误认为 Promise 构造函数内部是异步的（其实是同步执行）。

- 忽视了 await 后面的代码会被包装成微任务。

### 在处理 AI 生成的内容时，经常需要解析 Markdown，请问如何实现一个简单的 Markdown 渲染器？

Markdown 渲染本质是将特定规则的文本通过正则或抽象语法树（AST）转换为 HTML 标签。

- 基础实现：使用正则表达式匹配标题（#）、加粗（\*\*）、链接等语法并替换为对应标签。

- 性能优化：对于长文本，建议使用流式解析或分段解析，避免一次性正则匹配导致的卡顿。

- 安全性：必须对生成的 HTML 进行转义或使用 DOMPurify 进行过滤，防止 XSS 攻击。

- 扩展性：支持代码高亮（如 Prism.js）和数学公式（如 KaTeX）的集成。

常见坑：

- 正则表达式过于复杂导致回溯，引发性能问题。

- 忽略了嵌套语法的处理（如加粗文本中包含链接）。

### 请说明一下 CSS 中 Flex 布局和 Grid 布局的应用场景区别。

Flex 是一维布局系统，适合处理行或列的局部排列；Grid 是二维布局系统，适合处理复杂的整体框架设计。

- Flex 场景：导航栏、列表项对齐、垂直居中等线性排列。

- Grid场景：多行多列的仪表盘、复杂的响应式网格布局。

- 灵活性：Flex 侧重于内容的大小和分配；Grid 侧重于容器的结构定义。

- 兼容性：Flex兼容性极佳，Grid在老旧浏览器（如IE）中支持较差。常见坑：

- 在不需要二维控制时过度使用 Grid 增加复杂度。

- 混淆flex-basis和width的优先级。

### 谈谈 Promise.all 和 Promise.allSettled 的区别及各自的适用场景。

这两个方法都用于处理多个并发的 Promise，但对失败状态的处理逻辑完全不同。

- Promise.all：只要有一个失败就立即 reject，适用于所有请求必须全部成功的强关联场景。

- Promise.allSettled：无论成功还是失败都会等待所有结果返回，返回一个包含状态和值的对象数组。

- AI场景应用：在初始化AI助手时，如果需要加载多个配置插件，通常使用allSettled以保证部分插件失败不影响主流程。

- 返回值结构：allSettled 返回的是 { status: 'fulfilled', value: ... } 或 { status: 'rejected', reason: ... }。

#### 常见坑：

- Promise.all 失败后，其他正在进行的请求无法自动取消（需要配合 AbortController）。

- 忘记处理 Promise.all 的 catch 导致全局报错。

### 如何实现一个基础的防抖（debounce）函数？请手写代码。

防抖是指在事件触发后延迟执行，如果延迟时间内再次触发，则重新计时，常用于搜索框输入。

- 核心思路：利用闭包存储timer变量，每次触发前先clearTimeout。

- 参数处理：需要正确传递 this 上下文和 arguments 参数。

- 立即执行：可选支持第一次触发时是否立即执行。

```javascript
function debounce(fn, delay) {
    let timer = null;
    return function(...args) {
    if (timer) clearTimeout(timer);
    timer = setTimeout(() => {
    fn.apply(this, args);
    }, delay);
    };
}
```

#### 常见坑：

- 忘记清除旧的定时器。

- 丢失了原函数的 this 指向。

### 请解释什么是 SSE（Server-Sent Events），它与 WebSocket 有什么区别？

SSE 是一种基于 HTTP 的单向流式通信协议，非常适合 AI 逐字生成回复的场景。

- 通信方向：SSE是单向的（服务端向客户端），WebSocket是双向全双工的。

- 协议基础：SSE基于标准HTTP协议，无需握手升级；WebSocket需要独立的协议转换。

- 断线重连：SSE 内置了自动重连机制；WebSocket 需要开发者手动实现。

- 数据格式：SSE 默认传输文本流（UTF-8），WebSocket 支持二进制和文本。常见坑：

- 浏览器对同一域名的SSE连接数有限制（通常为6个）。

- 忘记在服务端设置 Content-Type: text/event-stream。

### 详细说明一下前端如何处理大模型的流式（Streaming）响应数据。

处理流式响应需要利用 Fetch API 的 body 属性，它是一个 ReadableStream 对象。

- 获取流：通过 response.body.getReader() 获取读取器。

- 循环读取：使用 while(true) 循环调用 reader.read()，根据 done 状态判断是否结

- 解码数据：使用 TextDecoder 将 Uint8Array 字节流转换为字符串。

- 缓冲区处理：由于网络包可能截断 JSON 字符串，需要维护一个 buffer，确保解析的是完整的 JSON 块。

```javascript
1 const reader = response.body.getReader();
2 const decoder = new TextDecoder();
3 while (true) {
4    const { done, value } = await reader.read();
5    if (done) break;
6    const chunk = decoder.decode(value, { stream: true });
7    // 处理 chunk，可能包含多个 data：标签
8 }
```

### 谈谈 Prompt Engineering 在前端开发中的应用，如何通过前端手段提升模型输出质量？

### 介绍一下什么是 Function Calling（函数调用），前端在其中扮演什么角色？

Function Calling 允许模型根据用户意图调用外部工具，前端负责定义工具 Schema 并执行具体的客户端逻辑。

- 定义阶段：前端或后端定义 JSON Schema，描述函数名、参数类型及描述。

- 识别阶段：模型判断需要调用函数，返回特定的 tool\_calls 结构。

- 执行阶段：前端拦截到调用请求，执行本地逻辑（如：查询京东订单、切换主题、打开弹窗）。

- 反馈阶段：将函数执行结果再次发送给模型，由模型总结并回复给用户。常见坑：

- 模型生成的参数格式不符合 Schema 预期，导致前端代码报错。

- 循环调用问题：模型不断调用函数导致死循环。

### 手写题：实现一个简单的状态管理，模拟 AI 聊天记录的增删改。

需要考虑消息的唯一 ID、角色（user/assistant）、状态（loading/error/success）以及内容。

- 使用数组存储消息对象。

- 遵循不可变原则（如 React 中的 setState），确保组件能正确触发重绘。

- 支持更新特定 ID 消息的内容（用于流式追加）。

```javascript
class ChatStore {
    constructor() {
    this.messages = [];
    }
    sendMessage(role, content) {
    const id = Date.now();
    this.messages = [...this.messages, { id, role, content, status: 'pending'
} ];
    return id;
}
updateMessage(id, newContent) {
    this.messages = this.messages.map(msg =>
    msg.id === id ? { ...msg, content: msg.content + newContent, status:
    'streaming' } : msg
    );
}
finishMessage(id) {
    this.messages = this.messages.map(msg =>
    msg.id === id ? { ...msg, status: 'success' } : msg
    );
}
}
```

#### 常见坑：

- 直接修改数组索引导致视图不更新。

- 在高频流式更新时没有做节流，导致 UI 渲染压力过大。
