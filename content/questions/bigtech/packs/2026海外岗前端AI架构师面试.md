### 简单介绍一下 Promise 的工作原理，以及在处理 AI 流式接口时，它和 async/await 有什么关系？

Promise 是 JS 处理异步操作的对象，代表一个未来可能完成或失败的操作及其结果值。

- 状态机制：包含 Pending、Fulfilled、Rejected 三种状态，状态转换不可逆。

- 链式调用：通过 .then() 和 .catch() 解决回调地狱，支持异步操作的顺序执行。

- 语法糖关系：async/await 是 Promise 的语法糖，使异步代码在书写上更接近同步逻辑，易于捕获异常。

- AI 场景应用：在调用 AI 接口时，通常使用 await 等待首包返回，再通过 ReadableStream 处理后续流式数据。

常见坑：

- 忘记处理 Promise 的 Reject 状态导致程序崩溃。

- 在循环中使用 await 导致请求串行，影响 AI 响应速度。

### 请说明 SSE (Server-Sent Events) 与 WebSocket 的区别，为什么 AI 对话通常选择 SSE?

SSE 是一种基于 HTTP 的单向通信机制，允许服务器向客户端推送数据；WebSocket 则是全双工的 TCP 通讯协议。

- 通信方向：SSE是单向的（服务端到客户端），WebSocket是双向的。

- 协议开销：SSE基于标准HTTP协议，更轻量，支持自动重连；WebSocket需握手切换协议。

- 数据格式：SSE 默认传输文本（UTF-8），适合 LLM 生成的 Markdown 文本流。

- 选型原因：AI对话主要是服务端持续输出，客户端只需发送一次Prompt，SSE的单向流特性完美契合且开发成本低。

常见坑：

- 浏览器对同一个域名的 HTTP 1.1 连接数限制（通常为 6 个）会导致 SSE 挂起。

- 代理服务器（如Nginx）开启了缓存导致流式效果失效。

### 如何使用 TypeScript 定义一个支持多模态输入的 AI 消息接口？

通过联合类型（Union Types）和辨析属性（Discriminant）来定义不同类型的消息内容，确保类型安全。

- 辨析属性：使用 type 字段区分 text、image、file 等消息类型。

- 泛型约束：为消息元数据（Metadata）提供泛型支持，方便扩展不同模型的特有字段。

- 只读属性：使用readonly 确保消息对象在流式追加过程中不被意外修改。

- 可选链与断言：在处理模型返回的不确定字段时，利用TS的可选链提高代码健壮性。常见坑：

- 使用 any 定义消息内容，导致在处理复杂多模态数据时失去类型检查。

### 请手写一个简单的流式数据解析器，将 ReadableStream 中的 Uint8Array 转换为字符串并打印。

利用 TextDecoder 和 ReadableStream 的 getReader 方法，循环读取并解码二进制数据块。

- 实例化解码器：创建 TextDecoder 实例，通常指定为 utf-8。

- 递归/循环读取：调用 reader.read() 获取 value 和 done 标志。

- 缓冲区处理：在流式传输中，需注意处理可能被截断的 UTF-8 字符（TextDecoder 的 stream 选项）。

- 异常处理：使用 try-finally 确保在读取出错或结束时释放 reader 锁。常见坑：

- 忽略了 stream: true 参数，导致跨包的中文多字节字符解码乱码。

- 没有正确处理流关闭的边界条件。

代码示例：

```typescript
async function parseStream(response) {
    const reader = response.body.getReader();
    const decoder = new TextDecoder("utf-8");
    while (true) {
    const { done, value } = await reader.read();
    if (done) break;
    const chunk = decoder.decode(value, { stream: true });
    console.log(chunk);
    }
}
```

### Web Worker 在前端 AI 应用中通常有哪些使用场景？

Web Worker 允许在后台线程运行脚本，避免阻塞主线程（UI 线程），提升用户体验。

- 密集型计算：在前端进行向量相似度计算或大规模数据预处理。

- 离线模型运行：在浏览器端运行轻量级 Transformers.js 模型。

- 语法高亮解析：对AI返回的长篇代码进行解析渲染，防止页面卡死。

- 消息分发：作为中转站处理复杂的 WebSocket/SSE 消息状态流转。

常见坑：

- 在 Worker 中尝试操作 DOM（Worker 无法访问 DOM）。

- 频繁的数据传输（PostMessage）导致的序列化开销过大。

### 在实现 AI 聊天对话框时，如何处理 CSS 布局以确保长文本自动换行且容器高度自适应？

使用 Flexbox 或 Grid 布局，并配合文本处理属性确保长字符串（如代码或无空格文本）不会溢出。

- 自动换行：设置 word-break: break-word 或 overflow-wrap: anywhere。

- 容器自适应：使用 height: auto 或 min-height，配合 Flex 的 flex-direction: column。

- 滚动锚定：利用 overflow-y: auto 并在内容更新时通过 scroll-into-view 保持底部可见。

- 预格式化处理：针对 AI 返回的 Markdown，需对 <pre> 标签设置 white-space: pre-wrap。

常见坑：

- 内部元素使用了 white-space: nowrap 导致整个对话框被撑开。

- 在移动端没有处理好键盘弹出后的视口高度（vh）缩放问题。

### AI 返回的长文本 Markdown 渲染很慢，且容易导致页面掉帧，你有哪些优化方案？

针对流式输出的特点，采用增量渲染和任务切片策略，减少DOM操作频率和计算压力。

- 节流渲染：不要每收到一个字符就触发 React/Vue 渲染，而是通过 requestAnimationFrame 或时间节流批量更新。

- 虚拟列表：当对话历史过长时，仅渲染可视区域内的消息组件。

- 增量解析：使用支持流式的 Markdown 解析器（如 md-it 的插件），只解析新追加的文本片段。

- 样式隔离：对代码高亮等耗时操作使用 CSS Containment 或 Web Worker，避免重排影响全局。常见坑：

- 每次更新都重新解析整个 Markdown 字符串，导致 CPU 占用随文本长度呈指数级增长。

- 频繁触发 React 的深度 Diff 导致输入框失去焦点或卡顿。

### 谈谈你在项目中是如何进行 Prompt Engineering 管理的？前端在其中扮演什么角色？

前端不仅是 UI 展示，更是 Prompt 的组装层和验证层，需要建立一套结构化的管理机制。

- 模板化管理：将 Prompt 拆分为 System Role、Context、User Input，在前端通过模板引擎动态组装。

- 变量注入：自动收集当前页面上下文（如选中文本、当前URL、用户偏好）注入到Prompt中。

- 长度控制：在发送前利用 Tiktoken 等库计算 Token 数量，自动截断过长的历史对话。

- 硬编码 Prompt 在代码里，导致修改困难且无法针对不同模型优化。

### 什么是 RAG（检索增强生成）？在前端实现 RAG 链路时需要注意什么？

RAG 通过从向量数据库检索相关文档并将其作为上下文喂给 LLM，解决模型幻觉和时效性问题。

- 引用溯源：前端需要高亮显示AI回答所引用的文档来源，并支持点击跳转。

- 检索反馈：提供“相关性”评价按钮，收集用户对检索结果的反馈以优化 Embedding 算法。

- 预处理优化：在上传文档到 RAG 系统前，前端可以进行初步的清洗（如去除 HTML 标签、分段预览）。

- 状态展示：清晰展示“搜索中...”、“阅读文档中...”、“生成回答中...”等中间状态。

- 检索到的上下文过长导致超过 LLM 的 Context Window，前端未做预警。

- 引用链接失效或权限控制不当导致用户无法查看原始文档。追问：

### 如何设计一个 AI Agent 的状态机？如何处理多步任务中的中断与恢复？

AI Agent 涉及思考、行动、观察的循环（ReAct 模式），需要一个强类型的状态机来管理。

- 状态建模：定义Idle、Thinking、Acting、Awaiting\_User、Success/Fail等明确状态。

- 序列化存储：将 Agent 的执行轨迹（Trace）实时持久化到 IndexedDB，支持刷新页面后恢复进度。

- 中断机制：利用AbortController实现任务撤回，并记录中断时的断点数据。

- 循环检测：前端需监控 Agent 是否陷入死循环（如反复执行同一个失败操作），并及时介入。常见坑：

- 状态更新与 UI 渲染不同步，导致 Agent 已经结束但界面仍显示加载中。

### 在前端集成向量数据库（如 Vector DB 的 JS SDK）时，如何保证 API Key 的安全？

前端环境是不安全的，严禁直接在客户端硬编码或存储具有高权限的 API Key。

- BFF 转发：通过后端（Node.js/Go）中转请求，API Key 存储在环境变量中，前端只调用同域接口。

- 临时凭证：使用类似 AWS STS 的机制，由后端下发具有时效性和权限限制的临时 Token。

- 代理层鉴权：在API网关层校验用户的Session/JWT，再由网关附加Key访问向量数据库。

- 环境变量混淆：虽然不能防黑客，但在构建时通过CI/CD注入不同环境的配置。

常见坑：

- 将 .env 文件提交到 Git 仓库。

- 在控制台打印包含敏感信息的请求日志。

### 谈谈 AI 应用中的 TTFT (Time to First Token) 指标，前端可以做哪些优化？

TTFT是衡量AI响应速度的关键指标，指从发送请求到接收到第一个字符的时间。

- 预连接优化：利用 <link rel="preconnect"> 提前建立与 AI 域名（如 api.openai.com）的连接。

- 减少Payload：精简发送到后端的上下文，只保留必要的历史消息。

- 边缘计算：利用 Edge Functions (如 Vercel/Cloudflare Workers) 在地理位置更近的节点处理请求。

- 视觉欺骗：在等待TTFT期间，立即展示用户的输入并播放占位动画，降低感知延迟。常见坑：

- 前端复杂的预处理逻辑（如大文件 Embedding）阻塞了请求的发出。

- 接口使用了过多的中间件导致首包延迟增加。

### 如何实现一个支持代码执行预览的 AI 组件（类似 Artifacts）？

- 沙箱隔离：使用 <iframe> 配合 sandbox 属性，或使用 Web Worker 运行逻辑，防止恶意代码攻击。

- 通信机制：通过postMessage将解析后的代码传递给沙箱，并处理双向通信。

- 依赖管理：动态加载代码所需的第三方库（如 React, Lucide-react），通常使用 ESM CDN（如 esm.sh）。

常见坑：

- 没处理好代码更新时的卸载逻辑，导致内存泄漏或多个定时器冲突。

- 沙箱权限开启过大（如 allow-same-origin），导致主站 Cookie 被窃取。

### 海外岗非常关注数据隐私（如 GDPR），在 AI 前端开发中如何落实这些合规要求？
