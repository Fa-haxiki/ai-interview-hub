我会把这道题当成标准的系统设计面试来答：**先澄清需求和规模，再给高层架构，然后讲数据流、关键取舍和难点，最后给演进路线。** RAG 单条链路里的解析、分块、检索、Rerank、生成我在其他题目里已经展开过，这里重点放在“系统”层面。

## 第一步：澄清需求

我会先花两三分钟问清楚这些问题，并说明每个答案对设计的影响：

- **数据源**：Confluence、飞书文档、工单系统、代码仓库、内部网页。异构源决定接入层的复杂度和解析策略。
- **规模**：文档量（十万级还是千万级页面）、用户数（几千人）、峰值 QPS（内部系统通常是个位数到几十）。这决定向量库选型和是否需要分片。
- **延迟目标**：首 token 2 秒内、完整回答 10 秒内，是内部知识库常见的可接受范围。
- **权限**：几乎一定有，而且是硬性要求。
- **多语言**：中英混合文档很常见，影响 Embedding 选型。
- **更新频率**：文档每天都在改，需要增量同步而不是每晚全量重建。
- **正确性要求**：HR 政策、财务流程这类问题答错代价高，必须带引用、允许拒答。

## 第二步：高层架构

```text
[数据源] Confluence / 飞书文档 / 工单 / 代码仓库
    │  连接器（全量 + 增量，携带权限信息）
    ▼
[数据接入与解析层] 统一中间格式：正文 + 标题层级 + 表格 + ACL
    ▼
[分块与索引流水线] 分块 → Embedding → 写向量库 + BM25 索引（异步任务队列）
    ▼
[存储] 向量库（含 ACL / tenant 元数据）+ 全文索引 + 原文对象存储
    ▲  带权限过滤的混合检索
    │
用户 → 网关/鉴权 → 权限服务 → 查询理解 → 检索服务（混合检索 + Rerank）→ 生成服务 → 回答 + 引用
                                          │                                  │
                                 评估与监控（trace / 评测集）        前端反馈（赞踩 / 纠错）
```

各层职责：

1. **数据接入与解析层**：每个数据源一个连接器，负责拉取、增量检测（基于 `updated_at` 或 webhook）、解析成统一中间格式。
2. **分块与索引流水线**：任务队列驱动，做分块、Embedding、写入向量库和 BM25 索引；失败可重试，可按文档粒度重建。
3. **检索服务**：混合检索（向量 + BM25）→ RRF 融合 → Rerank → 阈值截断，输出带引用信息的 Top-N。
4. **生成服务**：组装 Prompt、调用 LLM、流式输出、引用校验、拒答逻辑。
5. **权限服务**：把用户身份解析成组列表，交给检索服务作为过滤条件。
6. **评估与监控**：全链路 trace、离线评测集、线上采样打分。
7. **前端与反馈**：聊天界面、引用跳转、赞/踩、“答案有误”上报，反馈回流到评测集。

## 第三步：两条数据流

**离线索引流**：连接器发现变更 → 解析 → 分块 → Embedding → 写入（同一文档的旧 chunk 先标删再写新）→ 更新索引版本。这条流要的是吞吐和幂等，分钟级延迟就够。

**在线查询流**：鉴权 → 查询理解（改写、多轮指代消解、判断是否需要检索）→ 带权限过滤的混合检索 → Rerank → 生成 → 后处理 → 记录 trace。这条流要的是延迟和正确性。

两条流通过存储层解耦：索引流水线挂了，用户只是看到略旧的内容，查询不受影响。

## 第四步：关键设计决策与取舍

| 决策点 | 我的选择 | 理由与取舍 |
|---|---|---|
| 向量库 | pgvector 起步，规模上去换 Milvus / Qdrant | 内部系统通常百万级 chunk 以内，pgvector 少一个组件；元数据过滤性能下降是换库信号 |
| 模型是否自托管 | Embedding 和 Reranker 自托管，生成模型看合规要求 | 数据不出内网是很多企业的硬约束；小模型自托管成本可接受 |
| 缓存 | Embedding 缓存 + 语义缓存，key 含用户权限指纹 | 内部问题重复度高，但缓存必须按权限隔离，否则答案串号 |
| 多租户 | 单公司通常不需要，但按部门/BU 做 partition | 预留 `tenant_id` 字段，将来对外输出产品时可复用 |
| 编排框架 | 自研薄封装，不深度绑定框架 | 便于替换组件、做细粒度 trace |

## 第五步：难点

- **权限**：必须在检索阶段过滤，缓存和日志也要隔离，是系统里最不能出错的部分。
- **复杂文档解析**：飞书表格、Confluence 的嵌套页面、扫描版 PDF，解析质量直接决定上限。
- **多轮对话**：指代消解，以及判断这一轮要不要重新检索。
- **拒答与幻觉治理**：相关性阈值 + 强制引用 + 引用校验，宁可说“没找到”也不编。
- **冷启动评测**：上线前没有真实 query，先用 LLM 从文档生成候选问题，再由各部门的业务专家校对出几百条 golden set。

## 第六步：演进路线

1. **MVP（数周）**：单数据源、pgvector、纯向量检索、带引用的回答，先让一个部门用起来收集真实问题。
2. **质量提升**：混合检索 + Rerank、父子块、查询改写；接入权限服务。
3. **评估体系**：golden set + 自动评测进 CI，线上采样打分、反馈闭环，每次改动看数据说话。
4. **Agentic 与多源**：让模型决定查知识库还是查工单系统、是否多次检索；引入结构化数据查询。

面试里我会强调：每一步演进都由评测数据和用户反馈驱动，而不是一开始就把所有组件堆上去。

## 可能的追问

- 为什么不直接用现成的企业搜索 / 办公套件自带的 AI 问答？内部数据源杂、权限体系自定义、需要和内部系统深度集成时自研更可控；如果只是标准 SaaS 文档，现成产品反而更快。这个判断我会在澄清需求时就做。
- 如果 QPS 从几十涨到几千怎么办？检索和生成服务无状态水平扩展、向量库换分布式并按部门分片、Reranker 批量推理、生成层做模型路由和缓存；此时成本会取代延迟成为主要约束。
