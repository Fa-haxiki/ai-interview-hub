### 请简单介绍一下 CSS 的盒模型，以及 box-sizing 属性的作用。

盒模型是浏览器渲染引擎对HTML元素进行布局时所遵循的规则，它将所有元素看作一个矩形的盒子。

- 组成部分：由 content（内容）、padding（内边距）、border（边框）和 margin（外边距）组成。

- 标准盒模型：width 仅包含 content，不包含 padding 和 border。

- 怪异盒模型：width包含了content、padding和border。

- box-sizing：通过 content-box（标准）和 border-box（怪异）进行切换，实际开发中常用 border-box 以便控制尺寸。

- 忽略行内元素（inline）对某些盒模型属性（如 width/height）的不生效问题。

### 谈谈你对 JavaScript 原型和原型链的理解。

原型是JS实现继承的基础，每个对象都有一个指向其构造函数原型对象的内部链接。

- 构造函数与原型：每个函数都有prototype属性，指向其实例的原型对象。

- 隐式原型：每个实例对象都有 proto 属性，指向构造函数的 prototype。

- 原型链：当访问一个对象的属性时，如果自身没有，会沿着 proto 向上查找，直到 null。

- 终点：原型链的顶端是 Object.prototype.proto，即 null。

- 忽略了 constructor 属性的指向问题。

### 请解释一下闭包是什么，以及它在实际开发中的应用场景。

闭包是指有权访问另一个函数作用域中变量的函数，本质是函数与其词法环境的引用捆绑在一起。

- 形成条件：函数嵌套且内部函数引用了外部函数的变量。

- 核心作用：延伸了变量的作用范围，使其在外部函数执行完后不被销毁。

- 应用场景：封装私有变量、柯里化（Currying）、防抖节流、模块化开发。

- 内存影响：由于引用存在，可能导致变量无法被垃圾回收，需注意内存泄漏。

#### 常见坑：

### 浏览器中的事件循环（Event Loop）机制是怎样的？

事件循环是JS处理异步任务的核心机制，它通过任务队列协调主线程的执行。

- 任务分类：分为同步任务、微任务（Microtask）和宏任务（Macrotask）。

- 执行顺序：先执行同步代码，然后清空当前的微任务队列，最后取出一个宏任务执行。

- 微任务：Promise.then、MutationObserver、process.nextTick（Node）。

- 宏任务：setTimeout、setInterval、I/O、UI Rendering。

### 请手写一个基础的防抖（Debounce）函数。

防抖是指在事件被触发 $n$ 秒后再执行回调，如果在这 $n$ 秒内又被触发，则重新计时。

- 核心逻辑：利用闭包保存 timer 变量。

- 清除定时器：每次触发时先clearTimeout。

- 绑定上下文：确保 this 指向正确，参数正常传递。

```javascript
function debounce(fn, delay) {
    let timer = null;
    return function(...args) {
    if (timer) clearTimeout(timer);
    timer = setTimeout(() => {
    fn.apply(this, args);
    }, delay);
    };
}
```

- 忘记处理 this 指向。

- 忘记传递arguments参数。

### 说说 Promise 的几种状态，以及 Promise.all 和 Promise.race 的区别。

Promise是异步编程的一种解决方案，它有三种状态且状态一旦改变不可逆。

- 三种状态：Pending（进行中）、Fulfilled（已成功）、Rejected（已失败）。

- Promise.all：接收数组，所有 Promise 都成功才返回成功数组，有一个失败则立即返回失败。

- Promise.race：接收数组，返回最先改变状态（无论成功失败）的那个Promise的结果。

- 链式调用：then 方法返回的是一个新的 Promise 实例。

#### 常见坑：

- 误认为 Promise.all 里的任务是串行执行的。

### HTTP 状态码 204、301、302、304 分别代表什么含义？

状态码是服务器对请求处理结果的简短反馈。

- 204 No Content：请求成功，但响应报文不包含实体主体。

- 301 Moved Permanently：永久重定向，搜索引擎会更新索引。

- 302 Found：临时重定向，搜索引擎不会更新索引。

- 304 Not Modified：协商缓存命中，表示资源未改变，直接使用本地缓存。

### 简单实现一个浅拷贝和深拷贝。

浅拷贝只复制对象的第一层属性，深拷贝则递归复制所有层级。

- 浅拷贝实现：Object.assign({}, obj) 或扩展运算符 {...obj}。

- 深拷贝简单实现：JSON.parse(JSON.stringify(obj))，但无法处理函数、正则、循环引用。

- 递归实现：判断类型，递归遍历属性，处理循环引用（使用Map）。

```javascript
function deepClone(obj, hash = new WeakMap()) {
    if (obj === null || typeof obj != 'object') return obj;
    if (hash.has(obj)) return hash.get(obj);
    let res = Array.isArray(obj) ? [] : {};
    hash.set(obj, res);
    for (let key in obj) {
    if (obj.hasOwnProperty(key)) {
    res[key] = deepClone(obj[key], hash);
    }
    }
    return res;
}
```

#### 常见坑：

- 递归深拷贝时没有处理循环引用导致栈溢出。

- 忽略了 Date、RegExp 等特殊对象的处理。

### 谈谈 React 的 Fiber 架构，它解决了什么问题？

Fiber 是 React 16 引入的一种新的协调引擎，旨在提高复杂应用的响应速度。

- 解决痛点：旧版 Stack Reconciler 递归执行，任务过重时会阻塞主线程，导致掉帧。

- 核心机制：将渲染工作拆分为小单元（Fiber），支持任务的暂停、恢复和优先级排序。

- 双缓存技术：在内存中构建 workInProgress tree，完成后一次性提交到真实 DOM。

- 调度过程：利用requestIdleCallback（模拟实现）在浏览器空闲时执行任务。

#### 常见坑：

- 误认为 Fiber 提高了渲染的绝对速度（其实是提高了交互的流畅度）。

- 混淆了Render阶段（可中断）和Commit阶段（不可中断）。

### Vue 2 和 Vue 3 的响应式原理有什么区别?

Vue 3 改进了响应式系统，解决了 Vue 2 存在的局限性并提升了性能。

- Vue 2：基于 Object.defineProperty，通过 getter/setter 拦截属性。

- Vue 3：基于 ES6 Proxy，拦截整个对象的操作。

- 优势对比：Proxy 可以监听数组下标变化、动态添加/删除属性，且性能更好（懒代理）。

- 局限性: Vue 2 无法检测对象属性的添加或删除, 需要使用 \$set。

#### 常见坑：

- 认为 Proxy 会对嵌套对象进行全量递归（实际上是访问到哪层才代理哪层）。

- 忽略了 Proxy 对旧版浏览器的兼容性问题。

工程化是为了提高开发效率、降低维护成本、保证项目质量的一系列手段。

- 规范化：代码规范（ESLint/Prettier）、提交规范（Commitlint）、目录结构规范。

- 自动化：自动化测试、CI/CD持续集成与部署。

- 模块化/组件化：解耦业务逻辑，提高复用性。

- 工具化：脚手架（CLI）、构建工具、监控平台。

#### 三面（架构与综合能力）

### 如果让你从零设计一个前端监控系统，你会如何规划？

设计监控系统需要考虑数据采集、存储、清洗和可视化展示的全链路。

- 采集端：设计SDK，支持自动捕获（错误、性能、行为）和手动埋点，保证轻量化。

- 传输层：考虑上报频率、压缩数据、离线存储（IndexedDB）防止数据丢失。

- 后端处理：使用消息队列（Kafka）削峰填谷，实时计算引擎（Flink）处理报警。

- 展示层：看板展示核心指标、错误堆栈还原、用户行为回溯（录屏或日志流）。

#### 常见坑：

- 忽略了监控系统本身对业务性能的影响。

- 没考虑到海量数据下的存储和查询压力。

### 在技术选型时，你会考虑哪些因素？

技术选型不是选“最好的”，而是选“最合适的”。

- 业务匹配度：是否满足当前业务需求，是否有过度的技术债。

- 社区生态：文档是否完善，社区是否活跃，遇到坑是否容易找到方案。

- 团队上手成本：团队成员的技能储备，学习曲线是否平缓。

- 可维护性与扩展性：长期维护的成本，是否容易进行二次开发或迁移。

#### 常见坑：

- 盲目追求新技术（追新族）。

- 忽略了公司的技术栈统一要求。

### 谈谈你对前端组件库设计的看法，如何保证组件的高内聚低耦合？

优秀的组件库应该平衡灵活性和易用性。

- 职责单一：一个组件只做一件事，复杂的组件通过组合实现。

- 属性设计：Props命名规范，提供合理的默认值，支持受控与非受控模式。

- 样式管理：支持主题定制，避免全局样式污染（CSS Modules/CSS-in-JS）。

- 文档与测试：完善的API文档、交互示例以及高覆盖率的单元测试。

#### 常见坑：

- 组件Props过多导致逻辑极其复杂。

- 组件间存在隐式的依赖关系。

#### 追问：

- 如何处理组件库的按需加载？

### 面对复杂的业务需求，你如何进行需求拆解和任务分配？

需求拆解是将模糊的目标转化为可执行的技术方案的过程。

- 需求理解：先搞清楚业务目标和用户痛点，不盲目开始写代码。

- 模块拆解：按功能模块或页面维度拆分，识别出核心路径和边缘 Case。

- 技术方案评审：邀请团队成员参与，评估技术难点和潜在风险。

- 任务排期：预留缓冲时间（Buffer），按优先级排序，明确里程碑节点。

#### 常见坑：

- 拆解不够细致，导致后期任务延期。

- 忽略了前后端接口联调的时间成本。

### 你认为未来 2-3 年前端领域的发展趋势是什么？

前端领域正从单纯的页面开发向更深层次的工程化和智能化演进。

- 边缘计算与 Serverless：前端边界进一步扩大，SSR/ISR 成为常态。

- 提效工具：Rust/Go 赋能前端工具链（如 Turbopack, Rolldown），构建速度质变。

- AI + 前端：Copilot 辅助编程、UI 自动化生成、智能监控分析。

- 跨端融合：鸿蒙生态、小程序框架的演进，追求更接近原生的体验。

#### 常见坑：

- 回答过于笼统，没有具体的例子支撑。

- 表现出对新技术的排斥或盲目乐观。
