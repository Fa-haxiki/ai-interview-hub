### 请介绍一下 SSE（Server-Sent Events）的原理，它和 WebSocket 有什么区别？

SSE 是一种基于 HTTP 协议的服务器向客户端推送数据的技术，它建立一个长连接并以 text/event-stream 格式传输数据。

- 协议层：SSE基于标准HTTP，WebSocket是独立的二进制协议。

- 数据流向：SSE是单向的（服务器到客户端），WebSocket是全双工双向通信。

- 断线重连：SSE 内置了自动重连机制，WebSocket 需要开发者手动实现。

- 浏览器支持：SSE原生支持较好，但在IE上需要polyfill，且有最大连接数限制。常见坑：

- 忽略了浏览器对同一域名下 SSE 最大连接数（通常为 6 个）的限制。

- 如果要在 SSE 中实现双向通信，你会怎么做？

- 为什么 AI 聊天场景通常选择 SSE 而不是 WebSocket?

### 说一下 Fetch API 中的 ReadableStream，如何通过它读取流式响应？

Fetch 的 Response 对象暴露了 body 属性，它是一个 ReadableStream，允许我们在数据到达时逐块处理。

- 获取读取器：通过 response.body.getReader() 获取 reader 对象。

- 循环读取：使用 while 循环调用 reader.read()，根据 done 状态判断流是否结束。

- 文本解码：使用 TextDecoder 将 Uint8Array 字节流转换为可读字符串。

- 错误处理：需捕获网络中断或解析异常，并手动关闭读取器。

常见坑：

- 忘记处理 read() 返回的 value 可能不完整的情况（如中文字符被截断）。

- 没有正确处理流关闭后的清理逻辑。

### 谈谈 Promise.all 和 Promise.allSettled 的区别及应用场景。

这两个方法都用于处理多个并发的 Promise，但对失败的处理逻辑完全不同。

- Promise.all：只要有一个失败就立即 reject，适用于强依赖的一组请求。

- Promise.allSettled：无论成功失败都会等待所有 Promise 结束，并返回包含状态的对象数组。

- 返回值：all返回结果数组，allSettled返回包含status和value/reason的对象数组。

- 场景：all 用于批量获取必要数据，allSettled 用于执行互不影响的独立任务。

常见坑：

- 在 Promise.all 中没有对单个 Promise 做 catch 处理，导致一个失败全盘皆输。

### 在 AI 问答界面中，当消息列表非常长时，你会如何优化渲染性能？

长列表优化通常采用虚拟滚动（Virtual List）技术，只渲染可视区域内的DOM节点。

- 虚拟滚动：计算滚动高度，动态截取数据源中的一部分进行渲染，并用 padding 或 transform 撑起总高度。

- 动态高度：AI 回复长度不固定，需在渲染后通过 ResizeObserver 监听 DOM 高度并更新偏移量索引。

- 节点复用：尽量保持DOM结构稳定，减少浏览器的重排与重绘。

- 分片渲染：对于非首屏数据，可以使用requestIdleCallback进行后台预处理。常见坑：

- 滚动过快时出现白屏。

- 动态高度计算不准确导致滚动条抖动。

追问：

- 如果消息中包含图片，图片加载后高度变化如何处理？

### 如何设计一个 Prompt 模板引擎，支持变量替换和条件判断？

Prompt 模板引擎本质上是一个字符串解析器，需要支持占位符替换和简单的逻辑控制。

- 模板语法：定义类似 {{variable}} 的占位符，使用正则或 AST 进行匹配。

- 变量注入：提供 context 对象，通过递归或路径查找（如 user.name）获取值。

- 逻辑支持：支持 if/else 或 for 循环，可以通过简单的 DSL（领域特定语言）实现。

- 安全性：对用户输入进行转义，防止 Prompt 注入攻击。

常见坑：

- 嵌套变量处理不当导致解析失败。

- 模板过大时的解析性能问题。

### 详细说明一下前端如何处理大模型的 Token 流式输出并保证 UI 顺滑？

处理 Token 流的关键在于平衡 “实时性” 和 “渲染频率”，避免高频更新导致主线程阻塞。

- 缓冲区机制：建立一个消息队列（Buffer），将收到的Token先存入队列。

- 节流渲染：使用 requestAnimationFrame 配合缓冲区，每帧只取出部分 Token 更新到 state。

- 自动滚动：判断用户是否处于页面底部，若是则跟随滚动，若用户手动向上滚动则停止自动跟随。

- 状态管理：使用不可变数据结构更新消息列表，避免不必要的组件全量 re-render。常见坑：

- 每一个 Token 到达都触发一次 React setState，导致低端设备卡死。

- 自动滚动逻辑与用户手动滚动冲突，导致页面“乱跳”。追问：

- 如何检测用户是否手动向上滚动了？

### 你们是如何处理 AI 响应过程中的网络中断或异常的？

#### 难度：★★

异常处理需要覆盖网络层、协议层和业务逻辑层。

- 发生错误后，Loading状态没有清除，导致界面永久挂起。

- 滥用 Context 导致整个消息列表全量更新。

### 在电信业务场景下，AI前端如何处理数据安全和隐私保护？

电信数据敏感度高，前端需配合后端建立多重防护体系。

- 脱敏处理：在发送 Prompt 前，通过正则或本地模型识别并拦截手机号、身份证等敏感信息。

- 传输加密：全量使用 HTTPS，对敏感 Payload 进行二次加密。

- 权限控制：严格校验会话 Token，防止越权访问历史对话。

- 审计日志：记录用户的所有输入输出行为，用于事后溯源，但前端不存储敏感明文。

- 将敏感信息缓存在 localStorage 中被恶意脚本读取。

- 在报错日志中泄露了用户的输入内容。

### 如何评估一个 AI 前端应用的用户体验？有哪些关键指标？

AI应用的体验评估需要结合传统Web指标和AI特有指标。

- TTFT（Time to First Token）：首个字符返回的时间，直接影响用户的感知速度。

- 生成速度：平均每秒生成的Token数，反映了系统的吞吐能力。

- 交互成功率：用户输入到获得有效回复的比例，需剔除网络错误和模型幻觉。

- 用户满意度（CSAT）：通过点赞/点踩等显性反馈收集。

- 纠错成本：用户手动修改 Prompt 或重新生成的频率。

常见坑：

- 只关注LCP/FID等传统指标，忽略了AI响应的特殊性。追问：

- 如果TTFT过长，前端可以做哪些交互补偿？

### 针对低端设备，你会如何优化运行在浏览器端的 AI 模型（如 Transformers.js）？

浏览器端运行模型对计算资源要求极高，需从模型压缩和硬件加速两方面入手。

- 模型量化：使用4-bit或8-bit量化后的模型，显著降低显存占用和计算量。

- 硬件加速：优先使用WebGPU接口，相比WebGL能提供更高效的并行计算能力。

- 缓存策略：利用 Cache API 存储模型权重文件，避免重复下载。

- 算力分级：根据设备性能检测，动态决定是在本地运行小模型还是调用云端大模型。常见坑：

- 没做设备检测直接加载大模型导致浏览器崩溃。

- 忽略了WebGPU的兼容性问题。

追问：

- WebGPU 相比 WebGL 在 AI 计算上的核心优势是什么？
