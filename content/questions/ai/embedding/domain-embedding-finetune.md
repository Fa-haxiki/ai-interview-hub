我的默认答案是：先证明「领域术语和编号召不回」，再谈微调。很多所谓领域不行，其实是切词、稀疏检索和 query 改写没做；混合检索加领域分词，往往比动 Embedding 更划算。真要微调，按对比学习继续训，并接受全量重建索引。

## 什么时候才值得微调

看失败类型，不要看感觉。SKU、药名、内部接口号、法条编号被向量检索系统性漏掉，而 BM25 能中；或者同义的行话（「出网」对「离网」）永远排不到一起——这才是 Embedding 几何不对。如果只是 PDF 切坏、标题丢失、权限过滤错，微调解决不了。先在 golden set 上拆：稠密单独差、稀疏单独差，还是融合后仍差。只有稠密一路在领域词上明显塌，才进入微调讨论。

## 怎么做

核心是构造 query-doc 正对：搜索点击、客服 FAQ、工单与处理说明，不够就用 LLM 从文档合成问题，并人工抽检。负例不要只靠 in-batch，最好挖本领域难负例（易混型号、相邻条款）。训练仍是双塔对比学习；数据少就 LoRA，避免把通用语义全冲掉。BGE-M3 提供了只训稠密、或稠密/稀疏/多向量一起训的路径。指令前缀必须和线上一致，否则评测是一个空间、服务是另一个空间。

## 风险

1. **灾难性遗忘**：领域对变强，通用改写、跨语言、闲聊式提问变弱。要用领域集加一截通用检索集一起看。
2. **必须全量重建索引**：微调后的向量不在原空间，旧索引不能混用，迁移成本按文档量付。
3. **评估泄漏**：合成问题和切块来自同一批文档、或把测试 FAQ 拿去训练，分数会虚高。训练/验证/测试按业务线或时间切开。
4. **数据质量**：点击噪声、一题多答案被标成负例，会把边界学歪。宁缺毋滥。

很多团队走完评测会发现：加 BM25 / 稀疏向量、换领域分词、给 chunk 补标题，收益已经够了，微调可以不做。

## 可能的追问

- 微调 Embedding 和微调生成模型有何不同？前者改的是检索几何，必须重建索引；后者改的是写法和能力，知识仍建议用 RAG 注入。
- 数据只有几百对怎么办？优先 LoRA、冻结底层、难负例用教师模型过滤；数据再少就先别训，把力气放在混合检索和 golden set 上。
