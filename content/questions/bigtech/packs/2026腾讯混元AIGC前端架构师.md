### 请简述 JavaScript 的事件循环机制，并说明在处理 AI 流式响应时，宏任务与微任务的影响。

事件循环是JS处理异步操作的核心机制，通过执行栈、微任务队列和宏任务队列的协调运行。

- 执行顺序：同步代码 -> 微任务（Promise.then, MutationObserver） -> 渲染更新 -> 宏任务（setTimeout, I/O）。

- 流式响应影响：Fetch API 的流式读取通常在微任务中处理，如果微任务过重会阻塞 UI 渲染。

- 渲染时机：浏览器通常在宏任务执行前尝试渲染，频繁的微任务更新可能导致打字机效果不流畅。

- 任务拆解：对于复杂的 AI 文本解析，应考虑通过 requestAnimationFrame 或宏任务拆分长任务。常见坑：

- 认为Promise构造函数内部是异步的。

- 混淆 Node.js 环境与浏览器环境的事件循环差异。

### 实现 AI 打字机效果时，如何解决“字符吞噬”或“渲染卡顿”问题？

打字机效果不能直接透传后端 Stream 片段，需要建立前端缓冲区进行平滑调度。

- 缓冲区队列：将后端推送的 chunk 放入队列，前端按固定频率（如 50ms/字）取出。

- 调度器：使用 requestAnimationFrame 驱动字符渲染，确保与屏幕刷新率同步。

- 动态调速：当缓冲区堆积过多时加速播放，堆积过少时减速，保证视觉连续性。

- 文本处理：处理多字节字符（如 Emoji）被截断导致的乱码问题。

常见坑：

- 直接使用 setInterval 导致在后台标签页时逻辑堆积。

- 忽略了 Markdown 语法标记在未闭合时的渲染逻辑。

### 你们是如何处理 AI 接口超时和异常重试策略的？

针对AI接口响应慢的特性，需要多层次的容错机制。

- 指数退避重试：失败后按 1s, 2s, 4s 间隔重试，避免雪崩效应。

- 分段超时：设置首包超时（TTFT）和整体响应超时。

- 状态恢复：在重试时保留已输出的内容，实现断点续传（需后端支持）。

- 降级方案：当模型不可用时，自动切换到轻量级模型或展示友好提示。

- 自动重试导致用户 Token 消耗翻倍。

- 界面上没有明确的错误反馈，用户陷入无尽等待。
