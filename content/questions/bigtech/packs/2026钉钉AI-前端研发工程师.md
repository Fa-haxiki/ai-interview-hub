### 请简单介绍一下 SSE 和 WebSocket 的区别，为什么在 AI 对话场景中通常首选 SSE?

SSE 是一种基于 HTTP 的单向推送协议，相比 WebSocket 更加轻量且天然支持 HTTP 协议栈的所有特性。

- 协议开销：SSE基于标准HTTP，不需要像WebSocket那样进行协议升级握手，实现成本低。

- 传输方向：SSE 是单向的（服务端到客户端），符合 AI 生成内容的场景；WebSocket 是全双工的，在仅需接收文本流时显得过重。

- 断线重连：SSE 内置了自动重连机制，而 WebSocket 需要开发者手动实现心跳和重连逻辑。

- 兼容性：SSE在处理代理服务器、防火墙时比WebSocket更加友好，且支持gzip压缩。常见坑：

- 误以为SSE支持双向通信。

- 忽略了浏览器对同一个域名下 SSE 连接数的限制（HTTP/1.1 下通常为 6 个）。追问：

### 在处理 AI 返回的 Markdown 流式数据时，你是如何解决标签闭合问题的？

流式渲染需要实时解析不完整的字符串，通常通过增量解析或使用具备容错能力的解析库来保证 UI 不崩溃。

- 增量解析：使用如 marked 或 markdown-it 的插件，在解析前对未闭合的标签（如代码块的三个反引号）进行临时补全。

- 状态机：维护一个简单的状态机，记录当前是否处于代码块、加粗或链接的包裹中。

- 缓冲区：设置一个小型的缓冲区，避免在字符截断处（如 UTF-8 多字节字符中间）直接解析。

- 容错渲染：利用 React 或 Vue 的虚拟 DOM 机制，确保非法 HTML 结构不会导致整个页面白屏。常见坑：

### 说一下 JavaScript 中的事件循环机制，并解释它与 AI 响应卡顿的关系。

事件循环是 JS 处理异步任务的核心机制，如果主线程被长任务占用，会导致 AI 生成的文字无法及时渲染到屏幕上。

- 任务分类：分为宏任务（setTimeout, I/O）和微任务（Promise.then, MutationObserver）。

- 执行顺序：执行栈清空后，先处理所有微任务，再取一个宏任务执行，之后可能触发 UI 渲染。

- 渲染时机：浏览器通常在两次事件循环之间尝试渲染，如果JS执行时间过长（超过16ms），会造成掉帧。

- AI场景：解析大型JSON或渲染复杂的Markdown属于CPU密集型操作，容易阻塞主线程。

- 认为Promise是宏任务。

- 不理解 requestAnimationFrame 在事件循环中的位置。

### 请手写一个简单的防抖函数，并说明在 AI 搜索建议（Autocomplete）中为什么要用它。

防抖是指在事件触发后延迟执行，如果在延迟时间内再次触发，则重新计时，目的是减少高频操作带来的性能开销。

- 核心逻辑：利用闭包保存 timer 变量，每次触发时clearTimeOut。

- 搜索场景：避免用户每输入一个字母就向 LLM 发起一次昂贵的 API 调用。

- 资源节省：降低后端推理成本，减少前端渲染压力。

```javascript
function debounce(fn, delay) {
    let timer = null;
    return function(...args) {
    if (timer) clearTimeout(timer);
    timer = setTimeout(() => {
    fn.apply(this, args);
    }, delay);
    }
}
```

#### 常见坑：

- 忘记处理 this 指向和参数传递。

### 什么是 Token？在前端开发 AI 应用时，为什么需要关注 Token 计数？

Token 是模型处理文本的最小单位，前端关注 Token 主要是为了预估成本、管理上下文窗口以及优化用户体验。

- 定义：Token 可以是单词、子词或字符，不同模型的切分方式不同。

- 上下文限制：LLM 有最大 Token 输入限制，前端需要截断过长的历史对话。

- 计费参考：API调用通常按Token计费，前端展示进度或预估消耗需参考此数据。

- 截断策略：前端可以使用 tiktoken 等库在本地预估 Token 数，决定何时提醒用户或自动清理缓存。

常见坑：

- 简单地用字符串长度（length）等同于 Token 数。

- 忽略了 System Prompt 和历史消息占用的 Token。

### React 的 Fiber 架构是如何提升 AI 长文本渲染性能的？

Fiber 将渲染工作拆分为可中断的微小单元，使得浏览器在高频更新的 AI 对话场景下依然能保持响应。

- 时间分片：Fiber 允许 React 在处理大型 DOM 树更新时，将控制权交还给浏览器执行高优先级任务（如用户输入）。

- 优先级调度：AI 输出的文本更新可以被设置为较低优先级，而用户点击停止按钮等操作具有高优先级。

- 双缓存机制：在内存中构建新的Fiber树，完成后一次性提交到真实DOM，减少中间态的闪烁。

- 增量更新：配合流式数据，Fiber能更高效地处理频繁的小规模DOM变更。常见坑：

- 误认为Fiber缩短了总计算时间（实际上是分散了计算时间）。

- 不清楚哪些生命周期在 Fiber 架构下会被多次调用。

### 详细说明一下 LLM 的 Function Calling（函数调用）在前端是如何实现的？

Function Calling 是指模型根据用户意图输出结构化 JSON，前端解析该 JSON 并执行本地逻辑后将结果回传给模型。

- 定义 Schema：前端或后端定义工具函数的名称、描述和参数规范（通常遵循 JSON Schema）。

- 模型决策：模型判断是否需要调用工具，并返回 tool\_calls 字段。

- 本地执行：前端拦截到特定指令，执行对应的JS函数（如获取当前地理位置、查询数据库）。

- 结果回传：将执行结果封装成 tool 角色消息再次发送给模型，由模型生成最终回复。

- 模型生成的参数不符合 JSON 格式，前端解析报错。

### 遇到 AI 输出内容过长导致浏览器内存占用过高，你会如何排查和解决？

通过 Chrome DevTools 的 Memory 面板定位泄漏源，并针对长文本和频繁更新采取优化措施。

- 排查工具：使用 Heap Snapshot 对比不同时间点的内存快照，查找未释放的字符串或 DOM 节点。

### 手写题：实现一个带并发控制的请求调度器，模拟同时调用多个 AI 插件。

需要维护一个任务队列和当前正在执行的任务计数器。

```javascript
class TaskQueue {
    constructor(max) {
    this.max = max;
    this.count = 0;
    this.queue = [];
    }
    add(task) {
    return new Promise((resolve, reject) => {
    this.queue.push({ task, resolve, reject });
    this.run();
    });
    }
    run() {
    while (this.count < this.max && this.queue.length) {
    const { task, resolve, reject } = this.queue.shift();
    this.count++;
    task().then(resolve).catch(reject).finally(() => {
    this.count--;
    this.run();
    });
    }
    }
}
```

#### 常见坑：

- 任务失败后没有释放计数器导致队列阻塞。

- 没有返回 Promise 导致调用方无法 await。
