### 简单介绍一下 SSE 和 WebSocket 的区别，为什么 AI 对话场景多采用 SSE?

SSE 是基于 HTTP 的单向推送协议，而 WebSocket 是全双工的独立协议，AI 场景选择 SSE 主要是因为其轻量且原生支持断线重连。

- 协议层：SSE 运行在 HTTP 之上，开发成本低，兼容性好；WebSocket 是独立协议，需握手切换。

- 数据流向：SSE仅支持服务端向客户端推送；WebSocket支持双向实时通信。

- AI适配：大模型生成是增量的，SSE的text/event-stream格式天然契合流式输出。

- 维护成本：SSE 支持自动重连，且在代理服务器（如 Nginx）上的配置比 WebSocket 更简单。常见坑：

- 误以为 SSE 只能传文本，其实可以通过 Base64 传二进制。

- 忽略 HTTP/1.1 下 SSE 有 6 个并发连接限制的问题。

#### 2. 在处理多个 AI 模型并行调用时，Promise.all 和 Promise.allSettled 有什么区别？

### 在处理多个 AI 模型并行调用时，Promise.all 和 Promise.allSettled 有什么区别？

Promise.all 要求所有任务成功，而 Promise.allSettled 会等待所有任务结束并返回每个任务的状态结果。

- 失败处理：Promise.all 只要有一个 reject 就会立即触发 catch；allSettled 会记录每个 promise 的 status（fulfilled 或 rejected）。

- 返回值：all 返回结果数组；allSettled 返回包含 status 和 value/reason 的对象数组。

- 场景选择：AI场景中如果调用多个模型做对比，通常用allSettled以确保部分模型失败时不影响其他结果展示。

常见坑：

- 在 Promise.all 中忘记处理 catch 导致整个链路崩溃。

### 请手写一个简单的打字机效果函数，模拟 AI 逐字输出。

打字机效果核心是利用 setInterval 或递归的 setTimeout，将目标字符串按索引逐个提取并更新到 DOM 中。

- 核心逻辑：维护一个当前索引指针，每隔固定时间截取 substring(0, index++)。

- 性能考虑：对于超长文本，频繁操作DOM会有性能问题，可以考虑requestAnimationFrame。

- 交互细节：需要提供停止回调和结束状态标识。

常见坑：

- 忘记在组件销毁时清除定时器，导致内存泄漏。

- 字符包含 Emoji 或特殊字符时，按索引截取可能导致乱码。

```javascript
function typeWriter(text, callback, speed = 50) {
    let index = 0;
    const timer = setInterval(() => {
    if (index < text.length) {
    callback(text.substring(0, index + 1));
    index++;
    } else {
    clearInterval(timer);
    }
}, speed);
return () => clearInterval(timer);
}
```

### TypeScript 中的 Interface 和 Type 有什么区别？在定义 AI 接口返回数据时如何选择？

Interface 主要用于定义对象形状且支持声明合并，Type 更加灵活，支持联合类型、元组等定义。

- 能力范围：Type 可以定义基本类型别名、联合类型（如 'success' | 'error'），Interface 不行。

- 建议：定义 AI 响应结构等固定对象时首选 Interface，定义复杂的 Prompt 模板类型或状态联合时使用 Type。

### 算法题：给定一个字符串，找出其中不含有重复字符的最长子串的长度。

使用滑动窗口算法，维护一个左指针和右指针，利用哈希表记录字符最后出现的位置。

- 初始化：left 指针为 0，maxLen 为 0，Map 记录字符位置。

遍历：右指针向右移动，若遇到重复字符且在窗口内，则移动左指针到重复字符下一位。

- 更新：每次移动右指针后计算当前窗口长度并更新maxLen。常见坑：

- 左指针移动时没有判断重复字符是否在当前窗口内。

- 字符串为空或长度为1的边界情况。

#### 4. 什么是 AI Agent? 在前端实现一个 Agent 循环（Plan-Action-Observe）的核心逻辑是什么？

### 什么是 AI Agent？在前端实现一个 Agent 循环（Plan-Action-Observe）的核心逻辑是什么？

AI Agent 是能够自主规划并调用工具完成任务的系统，其核心是一个基于模型反馈的递归或循环逻辑。

- Plan（规划）：将用户目标分解为多个子任务或工具调用指令。

- Action（执行）：前端根据模型返回的 Tool Call 指令，执行对应的本地函数（如查询 API、操作 DOM）。

- Observe（观察）：将执行结果（成功/失败/数据）反馈给模型，由模型决定下一步动作。

- 终止条件：模型判断任务完成或达到最大迭代次数。

常见坑：

- 陷入无限循环（模型反复调用同一个错误工具）。

- 异步工具调用顺序错乱。

### 对话列表很长时，如何保证流畅度？如果对话中包含复杂的代码高亮和数学公式渲染呢？

核心方案是采用虚拟列表（Virtual List）技术，只渲染可视区域内的消息，并对重型组件进行按需加载。

- 虚拟滚动：使用react-window或react-virtuoso，固定或动态计算消息高度。

- 动态高度计算不准确导致列表跳动。

- 搜索对话内容时，虚拟列表无法直接定位。

### Node.js 作为全栈中间层，在处理 LLM 长连接请求时有哪些需要注意的地方？

Node.js 需处理好流的转发、超时管理以及内存压力，确保高并发下的稳定性。

- 超时控制：设置合理的 Socket 超时，防止模型响应过慢导致连接堆积。

- 异常捕获：监听 stream 的 error 事件，防止因模型侧断开导致 Node 进程崩溃。

- 安全校验：在中间层进行Token鉴权和敏感词过滤（Moderation）。

- 忘记设置 res.setHeader('Content-Type', 'text/event-stream')。

- 未处理客户端主动断开连接的情况，导致后端继续消耗 Token。
