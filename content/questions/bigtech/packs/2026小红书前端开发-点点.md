### 谈谈你对 JavaScript 异步编程的理解，Promise 和 async/await 有什么区别？

异步编程是JS处理耗时操作而不阻塞主线程的核心机制，async/await是Promise的语法糖，使异步代码看起来更像同步代码。

- Promise 使用链式调用 (.then/.catch)，解决了回调地狱问题。

- async/await 提供了更好的错误处理机制（try/catch）和更简洁的逻辑流。

- 每一个 async 函数都会隐式返回一个 Promise。

- await会暂停当前async函数的执行，等待Promise解决，但不会阻塞外部主线程。常见坑：

- 忘记在 async 函数中使用 try/catch 导致错误无法捕获。

- 在循环中使用 await 导致并行任务变成串行执行。

### 在 AI 聊天场景中，流式输出通常使用 SSE 协议，它和 WebSocket 有什么区别？

SSE 是基于 HTTP 的单向通信协议，适用于服务器向客户端持续推送数据的场景，如 AI 文本生成。

- 方向性：SSE 是单向的（Server -> Client），WebSocket 是全双工双向的。

- 协议基础：SSE基于标准HTTP协议，WebSocket是独立的TCP协议。

- 断线重连：SSE 内置了自动重连机制，WebSocket 需要手动实现。

- 数据格式：SSE 默认传输 UTF-8 文本，WebSocket 支持二进制和文本。常见坑：

- 忽略了 HTTP/1.1 下浏览器对同一域名的 6 个并发连接限制。

- 没处理好流式数据截断导致的 JSON 解析异常。

### 实现一个简单的防抖函数（debounce），并解释它在搜索框中的作用。

防抖是指在事件触发后延迟一段时间执行，如果在这段时间内再次触发，则重新计时。

- 核心原理：利用闭包存储定时器变量timer。

- 触发逻辑：每次调用先clearTimeout，再开启新的setTimeout。

- 作用：减少高频触发事件（如 input、resize）带来的性能开销。

- 应用：AI搜索建议、实时语法检查。

#### 常见坑：

- 闭包导致 this 指向错误，需要使用 apply 或箭头函数。

- 忘记处理函数参数传递。

追问：

- 节流（throttle）和防抖的区别是什么？

```javascript
function debounce(fn, delay) {
    let timer = null;
    return function(...args) {
    if (timer) clearTimeout(timer);
    timer = setTimeout(() => {
    fn.apply(this, args);
    }, delay);
    };
}
```

### 谈谈 CSS 中的 Flex 布局，如何实现一个 AI 聊天窗口的底部输入框自适应高度？

### TypeScript 中的 interface 和 type 有什么区别？在 AI 组件开发中如何选择？

interface 主要用于定义对象的结构，支持声明合并；type 更加灵活，可以定义联合类型、元组等。

- 扩展性：interface 通过 extends 扩展，type 通过 &（交叉类型）扩展。

- 合并：同名 interface 会自动合并属性，type 不允许同名。

- 能力：type 可以定义基本类型别名、联合类型（Type A | Type B）。

- 建议：定义组件Props或API返回结构优先用interface，定义复杂逻辑类型用type。

- 混淆了交叉类型和接口继承的覆盖规则。

### 手写题：给定一个字符串，找出其中不含有重复字符的最长子串的长度。

使用滑动窗口思想，维护一个左指针和右指针，通过哈希表记录字符出现的位置。

遍历字符串，右指针不断向右移动。

- 如果遇到重复字符，左指针跳到该字符上次出现位置的下一位。

- 过程中不断更新最大长度。

- 时间复杂度 $O(n)$ ，空间复杂度 $O(\min(m, n))$ 。

常见坑：

- 左指针回退问题：更新左指针时要取当前位置和旧位置的最大值。

- 字符串为空或长度为1的边界处理。

### React 的 Fiber 架构解决了什么问题？在 AI 文本长输出时如何保证页面不卡顿？

Fiber 引入了可中断的异步渲染机制，解决了 React 15 在处理复杂组件树时长时间占用主线程导致的掉帧问题。

- 任务拆分：将更新过程拆分为多个小单元（Fiber node）。

- 优先级调度：通过Scheduler根据任务优先级（如用户输入高于数据流更新）分配执行时间。

- 双缓存技术：在内存中构建新的 Fiber 树，完成后一次性提交到真实 DOM。

- AI 场景：流式输出频繁触发 setState，Fiber 可以确保高频更新下依然响应用户交互。常见坑：

- 在render阶段执行副作用操作。

- 错误地认为Fiber提高了渲染绝对速度，实际上它提升的是感知流畅度。追问：

### AI 产品的流式数据（Streaming）在前端如何高效渲染？如果返回的是 Markdown 格式，你会怎么处理？

流式渲染需要平衡“实时性”和“渲染性能”，避免每接收一个字符就触发一次全量解析。

- 缓冲区机制：设置一个微小的缓冲区或时间阈值，批量处理接收到的 chunk。

- 增量解析：使用支持流式解析的 Markdown 库（如 marked），或只对新增部分进行解析。

- 代码高亮：对于代码块，使用 Prism.js 或 lowlight，注意避免在主线程进行大规模正则匹配。

- 节点复用：确保 React/Vue 的 key 值稳定，减少 DOM 节点的销毁与重建。

常见坑：

- 每次 chunk 进来都全量重新渲染整个对话框。

- Markdown 标签未闭合导致的解析错误。

追问：

### 谈谈前端性能优化的指标，针对 AI 聊天应用，你最关注哪些指标？

除了传统的 LCP、FID 外，AI 产品更应关注与模型交互相关的自定义指标。

- TTFT (Time to First Token): 从发送请求到接收到第一个字符的时间，直接影响用户焦虑感。

- TPS (Tokens Per Second): 生成速度，反映了后端性能和网络稳定性。

- 交互稳定性：输入框在流式输出时的响应延迟。

- 资源加载：首屏渲染时间，尤其是AI相关的重型库（如渲染公式的KaTeX）。

- 只关注 DOMContentLoaded，忽略了模型响应的漫长等待。

### 你们项目中的 Prompt 是如何管理的？前端在 Prompt Engineering 中扮演什么角色？

前端不仅是 UI 的呈现者，也是 Prompt 的组装者和优化者。

- 模板化管理：在前端封装 Prompt 模板，根据用户输入动态填充参数。

- 上下文管理：负责维护对话历史，并根据Token限制进行裁剪或摘要。

- 调试工具：开发内部工具，对比不同 Prompt 版本下的模型输出效果。常见坑：

- 直接将敏感的 System Prompt 暴露在前端代码中。

### 实现一个并发控制函数，假设有 10 个 AI 任务需要调用接口，但浏览器并发限制为 3。

通过维护一个执行队列和当前运行计数器来实现。

- 核心逻辑：当计数器小于并发数时，从队列取任务执行。

- 递归触发：每个任务完成后，无论成功失败，都要触发下一个任务。

- 结果收集：使用 Promise.all 的思想或数组索引记录结果。
常见坑：

- 任务失败导致整个队列挂掉。

- 递归调用没有终止条件。

追问：

- 如果任务有优先级，你会怎么修改这个函数？

```javascript
async function limitConcurrency(tasks, limit) {
    const results = [];
    const executing = [];
    for (const task of tasks) {
    const p = Promise.resolve().then(() => task());
    results.push(p);
    if (limit <= tasks.length) {
    const e = p.then(() => executing.splice(executing.indexOf(e), 1));
    executing.push(e);
    if (executing.length >= limit) {
    await Promise.race(executing);
    }
    }
    }
    return Promise.all(results);
}
```

### 谈谈 Web Worker 的使用场景，在 AI 前端应用中它能做什么？

Web Worker 允许在后台线程运行脚本，避免阻塞主线程的 UI 渲染。

- 文本处理：在前端进行大规模的文本清洗、分词或向量相似度计算。

- 语法高亮：对超长代码块进行高亮解析。

- 离线模型：运行轻量级的 Transformers.js 等前端模型。

- 通信机制：通过 postMessage 传递数据，注意 Transferable Objects 优化性能。常见坑：

- 在 Worker 中尝试操作 DOM。

- 频繁的数据序列化开销超过了计算节省的时间。

### 如何处理 AI 生成内容中的长文本截断和 “阅读更多” 功能？

长文本处理需要考虑性能和视觉平滑度。

- CSS方案：使用line-clamp属性实现多行省略，但无法动态计算高度。

- JS方案：通过ResizeObserver监听容器高度，或计算字符长度。

- 交互细节：在流式输出过程中，应暂时禁用截断，待生成完成后再应用。

- 虚拟列表：如果对话非常多，使用虚拟列表（Virtual List）只渲染可视区域。常见坑：

- 截断位置刚好在 HTML 标签中间导致页面乱码。

### 如果让你从零设计一个 AI Agent 的前端架构，你会考虑哪些核心模块？

一个成熟的 AI Agent 前端架构应具备高扩展性和良好的状态管理。

- 通信层：封装SSE/WebSocket逻辑，支持请求拦截、重试及多模型切换。

- 状态层：管理对话历史、上下文窗口、Agent运行状态（思考中、生成中、工具调用中）。

- 插件/工具层：设计一套标准协议，让 Agent 可以调用前端定义的 UI 组件（如地图、图表、表单）。

- 渲染层：支持 Markdown、Latex、代码块及多模态内容（图片、语音）的展示。

- 缓存层：利用 IndexedDB 存储长对话历史，实现离线访问。

常见坑：

- 业务逻辑与 UI 耦合太深，导致难以适配不同的模型接口。

### 在小红书这种高并发、重交互的场景下，如何保证 AI 产品的稳定性？

稳定性是一个系统工程，需要从预防、监控到容灾全方位考虑。

- 降级策略：模型响应超时或失败时，自动切换到轻量级模型或展示友好提示。

- 监控体系：实时监控白屏率、JS错误率以及AI接口的异常状态码。

- 灰度发布：通过 Canary 发布逐步放量，观察核心指标变化。
常见坑：

- 忽略了弱网环境下的用户体验。
