### 在 AI 对话场景中，经常用到流式输出，请说明 SSE 和 WebSocket 的区别？

SSE 是基于 HTTP 的单向推送协议，而 WebSocket 是全双工的二进制协议，AI 问答通常优先选择 SSE。

- 协议属性：SSE是应用层HTTP协议，WebSocket是独立的TCP协议

- 数据流向：SSE仅支持服务端向客户端推送，WebSocket支持双向实时通信

- 断线重连：SSE 内置断线重连机制，WebSocket 需要开发者手动实现

- 传输效率：SSE 传输文本更轻量，WebSocket 适合高频交互或二进制传输常见坑：

- 认为SSE只能传输文本，其实可以通过Base64传二进制

### 请手写一个 Promise.all 的实现。

Promise.all 接收一个 Promise 数组，只有当所有 Promise 都成功时才返回结果数组，只要有一个失败就立即拒绝。

- 计数器机制：维护一个 count 变量记录已完成的数量

- 结果顺序：通过索引确保输出结果的顺序与输入数组一致

- 异常处理：任何一个 Promise 失败，直接调用 reject

- 类型兼容：输入可能包含非 Promise 值，需用 Promise.resolve 包裹常见坑：

- 结果数组的顺序写成了完成的先后顺序，而不是输入的索引顺序

- 忘记处理输入为空数组的情况

### 在处理 AI 联想输入时，防抖（Debounce）和节流（Throttle）有什么区别？

防抖是在事件触发后延迟执行，若期间再次触发则重新计时；节流是规定时间内只执行一次。

- 防抖场景：搜索框输入联想、窗口大小调整（resize）

- 节流场景：滚动加载（scroll）、模型生成过程中的进度更新

- 核心原理：防抖利用clearTimeout重新计时，节流利用时间戳或定时器锁死执行频率

- 用户体验：防抖关注最后一次操作，节流关注执行过程的平滑度常见坑：

- 在React组件中使用防抖时，没有处理组件卸载导致的内存泄漏

- 忘记处理 this 指向和参数传递

### 介绍一下 Fetch API 中的 ReadableStream，它在处理 LLM 响应时有什么作用？

ReadableStream 允许在数据全部到达前逐块读取内容，是实现 AI 逐字生成效果的核心。

- 异步迭代：通过 response.body.getReader() 获取读取器

- 内存优化：不需要等待整个 JSON 加载完毕，降低了长文本下的内存占用

- 实时性：读取到一块数据（chunk）后立即通过 TextDecoder 解码并渲染

- 状态控制：可以随时调用 reader.cancel() 停止接收模型输出常见坑：

- 忘记处理 TextDecoder 跨 chunk 解码导致的乱码问题（字节截断）

- 没有正确处理流关闭或异常中断的逻辑
