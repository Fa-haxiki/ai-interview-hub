### 请介绍一下浏览器中的事件循环机制，特别是微任务和宏任务的执行顺序。

事件循环是 JavaScript 处理异步操作的核心机制，通过任务队列的调度实现非阻塞 I/O。

- 执行栈清空后，优先处理所有微任务队列中的任务。

- 微任务执行完毕后，浏览器可能会进行渲染更新。

- 从宏任务队列中取出一个任务执行，执行完后再去检查微任务队列。

- 常见的微任务包括 Promise.then、MutationObserver，宏任务包括 setTimeout、I/O。常见坑：

- 误认为 Promise 构造函数内部是异步的（实际上是同步执行）。

- 忽视了 await 后面的代码会被包装成微任务。

#### 2. 在处理 AI 聊天的流式输出时，Fetch API 和传统的 XHR 有什么区别？

### 在处理 AI 聊天的流式输出时，Fetch API 和传统的 XHR 有什么区别？

Fetch API 原生支持 ReadableStream，能够逐块读取服务器返回的数据，非常适合处理 LLM 的流式响应。

- Fetch 更加现代化，基于 Promise 设计，语法更简洁。

- Fetch 支持通过 body.getReader() 获取流，实现边接收边解析。

- XHR需要通过监听onreadystatechange并处理partial response，实现较为繁琐。

- Fetch 默认不带 cookie，需要手动配置 credentials。

常见坑：

- 忘记处理 Fetch 的网络错误（只有网络故障才会 reject，404/500 需手动检查 ok 属性）。

- 在流式读取时没有正确处理 UTF-8 字符被切断的情况。

### 请说明一下TypeScript中interface和type的区别，以及在AI场景下如何选择？

interface 主要用于定义对象的结构，支持继承和声明合并；type 更加灵活，可以定义联合类型、元组等。

- interface 可以通过 extends 实现继承，type 通过 & 符号实现交叉类型。

- interface 支持同名自动合并，适合定义第三方库的配置接口。

- type 适合定义复杂的逻辑类型，如 AI 返回的多种 Message 类型的联合。

- 在定义 Agent 的工具函数（Tool Call）参数时，type 的联合类型表现更佳。常见坑：

- 在需要扩展性时使用了 type，导致无法进行声明合并。

- 混淆了交叉类型（&）和继承（extends）在处理同名属性冲突时的表现。追问：

### 针对AI聊天界面的长列表，你会如何优化性能以保证滚动流畅？

#### 5. 请手写一个基础的防抖（Debounce）函数，并说明它在 AI 搜索建议场景下的作用。

### 请手写一个基础的防抖（Debounce）函数，并说明它在 AI 搜索建议场景下的作用。

防抖是指在事件触发后延迟执行，如果在延迟时间内再次触发，则重新计时。

- 核心利用闭包存储 timer 变量。

- 每次触发时先clearTimeout，再开启新的setTimeout。

- 在 AI 搜索建议中，防止用户每输入一个字符就请求一次昂贵的 LLM 接口。

- 减少服务器压力和前端渲染频率。

常见坑：

- 忘记处理 this 指向和参数传递。

- 在 React 组件中使用时，没有配合 useCallback 导致每次渲染都生成新函数。追问：

- 节流（Throttle）和防抖的区别是什么？

- 如何给这个防抖函数增加一个“立即执行”的选项？

```javascript
function debounce(fn, delay) {
    let timer = null;
    return function(...args) {
    if (timer) clearTimeout(timer);
    timer = setTimeout(() => {
    fn.apply(this, args);
    }, delay);
    };
}
```

#### 1. React 的 Fiber 架构是如何提升复杂 AI 应用的响应性的？

### React 的 Fiber 架构是如何提升复杂Al 应用的响应性的？

Fiber 将同步的渲染过程转变为可中断的异步任务，避免了长耗时任务阻塞主线程。

- 引入了时间分片（Time Slicing），将大的更新拆分为多个小 Work Unit。

- 任务具有优先级，用户输入等高优先级任务可以打断低优先级的渲染。

- 在 AI 频繁更新文本（流式输出）时，Fiber 能够保证 UI 依然能响应用户点击或停止操作。

- 双缓存技术（current tree 和 workInProgress tree）保证了 UI 更新的原子性。常见坑：

- 误以为Fiber提升了渲染绝对速度（实际上是提升了交互流畅度）。

- 在 render 阶段执行了带有副作用的操作。

#### 2. 在处理 LLM 流式输出（Streaming）时，前端如何优雅地处理 Markdown 解析和代码高亮？

### 在处理 LLM 流式输出（Streaming）时，前端如何优雅地处理 Markdown 解析和代码高亮？

流式输出意味着数据是不完整的，解析器必须具备处理截断字符串的能力。

- 使用支持增量解析的 Markdown 库（如 markdown-it 或 micromark）。

- 针对代码块，利用 Prism.js 或 lowlight 进行高亮，注意在流式过程中只对已完成部分高亮。

- 采用 “缓冲-节流” 策略：不要每收到一个 token 就重新渲染整个 Markdown，而是按时间间隔更新。

- 使用 React.memo 或 Vue 的 v-once 优化已生成的历史片段。

常见坑：

- 每次 token 更新都全量解析 Markdown，导致 CPU 占用过高，页面卡顿。

- 标签未闭合时解析器报错或导致布局崩坏。

### 请谈谈你在项目中是如何管理 AI Agent 的多轮对话上下文（Context）的？

上下文管理的核心在于平衡 Token 消耗和记忆质量，前端需要维护一个结构化的消息列表。

### 什么是 Prompt Injection（提示词注入）？前端在安全方面能做哪些工作？

提示词注入是指恶意用户通过特定输入绕过系统设定的约束，操控 LLM 执行非预期任务。

- 输入过滤：在前端对用户输入进行敏感词扫描或正则校验。

- 结构化输入：避免将用户输入直接拼接在 System Prompt 中，使用官方推荐的 Chat 格式。

- 内容安全策略（CSP）：防止AI生成的恶意脚本在页面上执行。

- 敏感信息脱敏：在发送给LLM之前，前端识别并遮掩身份证、手机号等隐私信息。

常见坑：

- 认为安全完全是后端的事，前端不校验输入导致API滥用。

- 忽略了 AI 生成内容中可能包含的 XSS 攻击代码。

#### 5. 在构建 AI Agent 时，前端如何实现 Tool Call（工具调用）的交互反馈？

Tool Call 要求前端能够识别 LLM 返回的特定指令，并将其转化为 UI 组件或自动执行函数。

- 协议解析：解析 LLM 返回的 function\_call 字段，提取函数名和参数。

- 状态展示：在 UI 上显示“正在搜索”、“正在计算”等中间状态，提升用户预期。

- 权限确认：对于敏感操作（如删除、发送邮件），前端需弹出确认框，等待用户授权后再执行。

- 结果回填：将工具执行的结果再次发送给 LLM，触发下一轮生成。

- 工具执行时间过长导致前端超时，未做重试或报错处理。

- 参数校验不严导致前端执行工具函数时崩溃。

### 在构建 AI Agent 时，前端如何实现 Tool Call（工具调用）的交互反馈？

AI产品的用户体验高度依赖于模型的响应速度，需要监控特有的时间链路。

常见坑：

- 只监控接口响应时间，忽略了前端解析 Markdown 和渲染的时间开销。
