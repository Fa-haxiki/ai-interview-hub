### 简单介绍一下 SSE 和 WebSocket 的区别，为什么 AI 聊天场景多采用 SSE?

SSE 是基于 HTTP 的单向推送协议，而 WebSocket 是全双工协议。在 AI 文本生成的场景下，服务端向客户端持续输出内容是核心需求。

- 协议开销：SSE基于标准HTTP，开发成本低，支持断线重连，且天然支持流式输出。

- 传输方向：AI场景主要是服务端向客户端推送Token，不需要WebSocket的双向高频交互。

- 兼容性：SSE在处理代理服务器、防火墙时比WebSocket更稳健。

- 资源消耗：SSE相比WebSocket更加轻量，对服务器连接数的压力相对较小。常见坑：

- 误认为 SSE 只能传输文本，其实可以通过 Base64 传输二进制，但效率较低。

- 忽略了 SSE 在 HTTP/1.1 下有 6 个并发连接限制的问题。

- 如果要在 SSE 中实现用户中断生成，前端应该怎么做？

### 谈谈你对 CSS 容器查询（Container Queries）的理解，它和媒体查询有什么区别？

容器查询允许开发者根据父容器的大小而非视口（Viewport）的大小来调整组件样式，这对于 AI 侧边栏等动态布局非常有用。

- 核心区别：媒体查询基于屏幕尺寸，容器查询基于父元素尺寸。

- 应用场景：适用于高度组件化的开发，组件可以根据被放置的位置自动适配。

- 语法要求：需要先通过 container-type 声明父容器。

- 性能考量：浏览器对容器查询做了优化，但在复杂嵌套下仍需注意重绘压力。常见坑：

- 忘记给父元素设置 container-type 导致查询失效。

#### 5. 手写代码：实现一个带并发限制的 Promise.allSettled。

该功能要求在保证所有 Promise 都有结果的前提下，控制同时执行的任务数量。

- 状态记录：需要记录每个 Promise 的结果（status 和 value/reason）。

- 队列管理：维护一个当前正在执行的任务计数器，当计数器小于限制值时，从任务池取新任务。

- 递归/循环：任务完成后触发下一个任务，直到所有任务完成。

- 最终返回：当所有任务处理完毕，resolve结果数组。

代码示例：

```javascript
async function limitConcurrent(tasks, limit) {
    const results = [];
    const executing = new Set();
    for (const task of tasks) {
    const p = Promise.resolve(task()).then(
    val => ({ status: 'fulfilled', value: val }), 
    err => ({ status: 'rejected', reason: err })
    );
    results.push(p);
    executing.add(p);
    p.finally(() => executing.delete(p));
    if (executing.size >= limit) {
    await Promise.race(executing);
    }
    }
    return Promise.all(results);
}
```

- 忘记处理任务报错的情况，导致整个流程挂掉。

- 计数器逻辑错误导致并发数超过限制或任务丢失。

### 算法题：给定一个字符串，找出其中不含有重复字符的最长子串的长度。

使用滑动窗口（双指针）来维护一个不含重复字符的区间。

- 窗口移动：右指针向右移动扩大窗口，将字符存入哈希表。

- 冲突处理：当遇到重复字符时，左指针移动到重复字符上次出现位置的下一个位置。

- 长度更新：每次移动右指针后，计算当前窗口长度并更新最大值。

- 时间复杂度：O(n)，每个字符最多被访问两次。

常见坑：

- 左指针回退问题：更新左指针时要取当前位置和冲突位置的最大值。

- 边界条件：空字符串或全重复字符串的处理。

### React 的 Fiber 架构是为了解决什么问题？在 AI 聊天这种长文本渲染场景下有何优势？

Fiber 架构引入了可中断的异步渲染机制，解决了 React 15 在处理大量 DOM 更新时主线程阻塞导致的卡顿问题。

- 任务拆分：将渲染工作拆分为多个小任务（Work Unit），利用浏览器空闲时间执行。

- 优先级调度：AI场景中，用户输入和停止按钮的响应优先级高于文本流的渲染。

- 增量渲染：在长对话列表中，Fiber可以确保新消息的插入不影响页面的滚动流畅度。

- 协调过程：双缓存技术（current tree 和 workInProgress tree）保证了 UI 更新的原子性。常见坑：

- 误以为Fiber提高了渲染绝对速度，实际上它提升的是用户感知的流畅度。

- 混淆了 Reconciliation（协调）和 Commit（提交）阶段的可中断性。追问：

- 既然Fiber是异步的，那useEffect是在什么时候执行的？

### AI 应用中经常需要处理流式输出（Streaming），前端如何优雅地处理这种状态更新？

流式更新频率极高（每秒多次），直接频繁 Kerala 会导致严重的性能问题。

- 缓冲区策略：建立一个缓冲区，每隔一定时间（如 100ms）或达到一定字符数后再批量更新状态。

- 局部更新：避免整个对话列表重新渲染，只针对当前正在生成的Message组件进行局部更新。

- 非状态变量：对于不需要触发渲染的中间数据，使用useRef存储。

- 渲染优化：利用 memo 或 useMemo 锁定已生成的历史消息。

常见坑：

- 每次 Token 返回都触发全局 Context 更新，导致整个页面卡死。

- 忽略了流式输出过程中的自动滚动逻辑，导致用户体验不佳。

- 如果用户在生成过程中向上滚动，你的自动滚动逻辑应该如何处理？

RAG 是通过检索外部知识库来增强 LLM 回答准确性的技术。前端不仅是 UI 展示，还参与数据处理和交互链路。

### 在开发 AI Agent 任务编排界面时，你会如何设计底层的状态模型？

Agent 编排涉及节点、连线、执行状态等复杂数据，需要一个高扩展性的状态结构。

- 图结构数据：使用邻接表或节点数组存储，每个节点包含ID、类型、配置参数及运行状态。

- 状态机：利用有限状态机（FSM）管理每个节点的“待执行、执行中、成功、失败”状态。

- 订阅机制：采用原子化状态库（如 Zustand 或 Recoil）实现节点级的局部更新。

- 撤销重做：设计Action日志，支持编排过程中的Undo/Redo。

常见坑：

- 将所有节点数据塞进一个巨大的嵌套 Object，导致更新时性能极差且难以维护。

- 状态设计没有考虑到异步执行过程中的中间态。

### 谈谈 Prompt Injection（提示词注入）攻击，前端能做哪些防护？

提示词注入是通过恶意输入绕过模型设定的安全限制。虽然核心防御在后端，但前端是第一道防线。

- 输入校验：对用户输入进行敏感词过滤或长度限制。

- 模板隔离：在前端构建 Prompt 模板时，确保用户输入部分有明确的分隔符。

- UI引导：通过结构化输入（如表单）替代纯文本框，减少用户直接接触底层Prompt的机会。

- 输出清洗：对AI返回的内容进行二次检查，防止其输出恶意脚本。

常见坑：

- 认为只要前端做了限制就安全了，忽略了攻击者可以直接调用API。

- 过于严格的过滤导致正常用户体验受损。

7. 手写代码：实现一个简单的流式解析器，将 SSE 返回的 data: {"text": "xxx"} 格式解析并合并。

需要处理数据分片到达的情况，确保 JSON 解析不报错。

- 缓冲区累加：将每次到达的 chunk 累加到缓冲区字符串。

- 消息拆分：根据 \n\n 分隔符拆分出完整的消息行。

- 格式提取：使用正则或字符串操作去掉 data：前缀。

- 异常处理：捕获 JSON.parse 的错误，处理不完整的 JSON 片段。

代码示例：

```javascript
function parseSSEStream(chunk, buffer) {
    buffer += chunk;
    const lines = buffer.split('\n');
    const remaining = lines.pop(); // 留存不完整的行
    const messages = lines
    .filter(line => line.startsWith('data: '))
    .map(line => {
    try {
    return JSON.parse(line.replace('data: ', '')).text;
    } catch (e) {
    return '';
    }
    });
    return { content: messages.join('', newBuffer: remaining };
}
```

#### 常见坑：

- 忽略了 chunk 可能会在 data：关键字中间断开的情况。

- 没处理 [DONE] 等特殊结束标识。

### 算法题：实现一个 LRU（最近最少使用）缓存，用于存储 AI 模型的上下文或搜索结果。

LRU 要求在 O(1) 时间复杂度内完成 get 和 put 操作。

- 数据结构：利用 JavaScript 的 Map 对象，它会按照插入顺序维护键值。

- get 操作：如果键存在，先删除再重新插入，使其移动到“最近使用”的位置。

- put 操作：如果键存在则更新并移动；如果超容，则删除 Map 中的第一个元素（最旧的）。

- 边界处理：处理容量为0或负数的情况。

常见坑：

- 使用普通 Object 加时间戳，导致 get/put 时间复杂度达到 O(n)。

- 忘记在更新值时也调整元素顺序。

### 场景题：AI 聊天记录非常多（上万条），如何保证滚动平滑且不卡顿？

- 虚拟列表：只渲染视口内及其上方/下方的少量节点（Buffer）。
