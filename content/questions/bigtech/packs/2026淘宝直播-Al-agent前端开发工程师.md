### 请简述一下 SSE 和 WebSocket 的区别，在 AI 流式输出场景下你会如何选择？

SSE 是基于 HTTP 的单向通信协议，而 WebSocket 是全双工的独立协议，在 AI 问答场景中 SSE 往往因其轻量和自动重连特性更受青睐。

- 协议层：SSE运行在HTTP之上，支持自动重连；WebSocket是独立协议，需要处理握手和心跳。

- 数据流向：SSE仅支持服务端向客户端推送；WebSocket支持双向实时通信。

- 浏览器支持：SSE原生支持TextStream处理，非常适合LLM的逐字生成效果。

- 复杂性：SSE 实现简单，对现有 HTTP 架构兼容性好，无需额外配置网关支持。

- 忽略了 HTTP/1.1 下浏览器对 SSE 有 6 个并发连接的限制。

- 忘记在服务端设置 Cache-Control: no-cache。

### 在处理AI响应的长列表消息时，如何实现自动滚动到底部，并保证用户手动向上滚动时不被干扰？

通过监听容器的scroll事件判断用户是否处于底部，仅在处于底部时随新内容自动滚动。

- 判定逻辑：通过 scrollHeight - scrollTop === clientHeight 判断是否触底。

- 阈值处理：通常会预留10-20px的偏差量，防止因浮点数计算导致的判定失败。

- 行为控制：使用 scrollIntoView({ behavior: 'smooth' }) 或直接修改 scrollTop。

- 状态锁：当用户手动向上滚动超过一定距离时，关闭自动滚动开关。

- 在 React/Vue 中更新数据后立即操作 DOM，导致获取的 offsetHeight 是旧的。

- 频繁触发滚动事件导致性能抖动。

### 请手写一个具有并发限制的请求调度器，模拟同时调用多个AI接口的场景。

该调度器需要维护一个执行队列和一个等待队列，确保当前运行的任务数不超过预设的 limit。

- 核心结构：内部维护 count 计数器和 queue 数组。

- 任务入队：每次 add 任务时判断 count 是否小于 limit。

- 递归执行：任务完成后，在finally回调中取出队首任务继续执行，直到队列清空。

- 结果返回：add 方法应返回一个 Promise，以便外部获取单个任务的结果。常见坑：

- 忘记处理任务执行失败的情况，导致计数器无法重置，后续任务阻塞。

- 没有返回 Promise，导致调用方无法 await 结果。

```javascript
class TaskQueue {
    constructor(limit) {
    this.limit = limit;
    this.count = 0;
    this.queue = [];
    }
    async add(fn) {
    if (this.count >= this.limit) {
    await new Promise(resolve => this.queue.push(resolve));
    }
    this.count++;
    try {
    return await fn();
    } finally {
    this.count--;
    if (this.queue.length) this.queue.shift()();
    }
    }
}
```

#### 6. 解释一下 JS 中的事件循环（Event Loop），并说明宏任务与微任务在处理 AI 消息推送时的先后顺序。

### 解释一下 JS 中的事件循环（Event Loop），并说明宏任务与微任务在处理AI消息推送时的先后顺序。

事件循环是JS处理异步任务的核心机制，微任务会在当前宏任务执行完后、渲染前清空。

- 执行顺序：同步代码 -> 微任务（Promise.then, MutationObserver） -> 渲染 -> 宏任务（setTimeout, I/O）。

- AI 场景：从 SSE 接收到的数据回调属于宏任务，而处理数据状态更新的 Promise 属于微任务。

- 渲染时机：微任务执行完后浏览器会尝试进行 UI 渲染，因此在微任务中频繁更新状态可能导致掉帧。

常见坑：

- 误以为 Promise 构造函数里的代码是异步的。

- 在微任务中递归创建微任务导致页面卡死。

### AI流式输出时，前端如何解决“打字机”效果带来的频繁DOM渲染导致的性能问题？

核心思路是降低渲染频率，通过缓冲区（Buffer）或节流机制来合并更新。

- 缓冲区机制：将 SSE 接收到的字符先存入 Buffer，每隔 50-100ms 批量更新一次状态。

- 增量更新：仅对当前正在生成的最后一条消息进行局部更新，避免全量列表Diff。

- 样式优化：使用 contain: content 等 CSS 属性限制重绘范围。

- 动画处理：打字机光标使用 CSS 动画而非 JS 模拟，减少主线程压力。

- 每次收到一个字符都触发一次 setState，导致 React 频繁执行 Fiber 调和。

- 忽略了长文本下的内存占用问题。

### 谈谈 React Fiber 架构对 AI 聊天机器人这类长文本更新场景的意义。

Fiber 通过时间分片（Time Slicing）将渲染工作拆分为小单元，防止长文本更新阻塞主线程。

- 任务拆分：在 Diff 阶段，Fiber 允许中断和恢复，确保高优先级的用户输入能及时响应。

- 优先级调度：AI字符更新可以设置为较低优先级，而用户点击、滚动设置为高优先级。

- 并发模式：利用 useTransition 等 Hook，可以让 AI 文本的渲染在后台进行，不卡顿 UI。

- 稳定性：避免了旧版 React 递归 Diff 导致的调用栈过深问题。

常见坑：

通过预设引导、结构化约束和反馈机制来增强交互的可控性。

- 引导建议：在输入框上方提供快捷指令（Quick Replies），规范用户输入。

- 结构化输出：强制要求模型返回 JSON，前端通过 UI 卡片（Card）展示，而非纯文本。

- 进度反馈：对耗时操作展示分步进度（如：正在搜索、正在总结、正在出图）。

- 容错编辑：允许用户对 AI 生成的结果进行二次微调，并反馈给模型学习。常见坑：

- 完全依赖模型的自由发挥，导致 UI 布局频繁崩坏。

- 缺乏对模型“幻觉”的提示。
