### 简单介绍一下 SSE (Server-Sent Events) 的原理，它和 WebSocket 有什么区别？

SSE是一种基于HTTP协议的单向推送技术，允许服务器向客户端实时发送数据流，常用于AI聊天的打字机效果。

- 协议基础：基于标准 HTTP 协议，默认支持断线重连。

- 数据流向：单向通信，仅支持服务端向客户端推送，客户端发送请求需另开 HTTP。

- 数据格式：传输文本格式的事件流（text/event-stream）。

- 轻量化：相比 WebSocket 更加轻量，对防火墙和代理服务器更友好。

- 误以为SSE支持二进制传输。

- 忽略了 HTTP/1.1 下浏览器对同一域名的并发连接限制（通常为 6 个）。追问：

- 如果在 HTTP/1.1 下达到连接上限，你会如何优化？

- 如何在 SSE 请求中添加自定义 Header?

### 在处理 AI 生成的流式数据时，如何使用 Fetch API 读取 ReadableStream?

通过 Fetch 返回的 Response 对象的 body 属性获取 ReadableStream，并使用 reader 循环读取 chunk。

- 获取 reader: 调用 response.body.getReader()。

- 循环读取：使用 while 循环配合 reader.read() 获取 value 和 done 状态。

- 解码数据：使用 TextDecoder 将 Uint8Array 转换为字符串。

- 异常处理：需处理网络中断或 reader 提前释放的情况。

常见坑：

- 忘记处理 chunk 被截断导致 JSON 解析失败的情况。

- 没有正确关闭 reader 导致内存泄漏。

追问：

- 遇到半个 UTF-8 字符截断时，TextDecoder 是如何处理的？

#### 4. 手写代码：实现一个简单的 Promise 队列，限制并发数为 3。

通过维护一个当前执行中的任务计数器，在任务完成后自动触发下一个任务。

- 核心逻辑：维护一个待执行任务数组和当前运行数。

- 递归触发：每个任务执行完毕后，运行数减一，并从数组中取出新任务执行。

- 返回值处理：通常需要返回一个 Promise 以支持链式调用。

- 边界条件：处理空数组或并发数大于任务数的情况。

常见坑：

- 任务报错导致队列中断。

- 无法正确处理 Promise 的 resolve/reject 状态传递。

```javascript
class PromisePool {
    constructor(limit) {
    this.limit = limit;
    this.running = 0;
    this.queue = [];
    }
    add(fn) {
    return new Promise((resolve, reject) => {
    this.queue.push({ fn, resolve, reject });
    this.run();
    });
    }
    run() {
    while (this.running < this.limit && this.queue.length) {
    const { fn, resolve, reject } = this.queue.shift();
    this.running++;
    fn().then(resolve).catch(reject).finally(() => {
    this.running--;
    this.run();
    });
    }
    }
}
```

### 谈谈你对 Prompt Engineering（提示工程）的理解，前端开发中如何管理 Prompt?

提示工程是通过设计、优化输入文本来引导 LLM 输出高质量结果的技术。

- 核心要素：角色设定（Role）、上下文（Context）、任务指令（Task）、输出约束（Constraint）。

- 常用技巧：Few-shot（少样本提示）、Chain of Thought（思维链）。

- 前端管理：将 Prompt 模板化，通过变量插值动态生成，避免硬编码。

- 版本控制：对复杂的 Prompt 进行版本管理，确保效果可追溯。

常见坑：

- 将敏感业务逻辑或 API Key 直接暴露在前端 Prompt 中。

- 忽略了不同模型对同一 Prompt 的理解差异。

### 如何判断一个变量是否为数组？请列举至少三种方法。

最推荐的方法是使用 Array.isArray()，它是 ES5 引入的专门用于数组检测的 API。

- Array.isArray(obj)：最可靠，能跨iframe工作。

- obj instanceof Array：基于原型链，但在多窗口环境下可能失效。

- Object.prototype.toString.call(obj) === '[object Array]'：最稳健的传统方法。

- obj.constructor === Array：容易被修改原型导致失效。

常见坑：

- 使用 typeof 只能得到 object。

### AI 聊天应用中，当模型输出很长的 Markdown 内容时，如何保证渲染性能不卡顿？

流式渲染长文本时，频繁的 DOM 更新和 Markdown 解析是性能瓶颈，需要通过节流和增量渲染来优化。

- 节流更新：不要每收到一个字符就重新渲染，可以设置50-100ms的时间窗口批量更新。

- 增量解析：使用支持流式解析的 Markdown 库，或者只对新产生的片段进行解析拼接。

- 虚拟列表：当历史消息过多时，使用虚拟滚动技术只渲染可视区域内的消息。

- Web Worker：将复杂的 Markdown 解析逻辑移出主线程，避免阻塞 UI。

常见坑：

- 每次更新都全量重新渲染整个 Markdown 组件。

- 在流式输出过程中频繁触发页面重排（Reflow）。

追问：

- 如果 Markdown 中包含复杂的数学公式（Latex），渲染压力更大，你会怎么处理？

### 请详细描述一次 RAG（检索增强生成）的完整前端交互流程。

RAG 流程涉及用户提问、向量检索、上下文拼接和模型生成四个核心阶段。

- 触发阶段：用户输入问题，前端调用后端接口。

- 检索阶段：后端将问题转化为向量，在向量数据库中检索相关文档片段。

- 增强阶段：将检索到的知识片段作为上下文，配合 System Prompt 喂给 LLM。

- 生成阶段：LLM根据上下文回答问题，前端通过流式接口展示结果并标注引用来源。常见坑：

- 忽略了引用来源（Citations）的展示，导致用户无法核实信息。

- 检索到的内容过长，超过了模型的上下文窗口限制。

### 在开发 AI Agent 时，如何处理 Function Calling（函数调用）的逻辑？

Function Calling 允许模型根据需求调用外部工具，前端需要处理模型返回的调用指令并执行相应逻辑。

- 定义工具：在请求模型时，通过 tools 参数定义函数名、描述和参数 Schema。

- 识别调用：解析模型返回的 tool\_calls，获取函数名和参数。

- 执行与反馈：前端或后端执行该函数，并将执行结果再次发送给模型。

- 状态展示：在 UI 上展示“正在搜索”、“正在计算”等中间状态，提升用户体验。常见坑：

- 模型生成的参数不符合 JSON 格式或 Schema 要求，缺乏校验。

- 函数执行时间过长导致连接超时。

追问：

- 如果模型一次性要求调用多个函数，你应该如何处理？

### 谈谈前端如何防御提示词注入（Prompt Injection）攻击？

提示词注入是指用户通过特定输入绕过系统设定的约束，前端需配合后端进行多层防护。

- 输入过滤：对用户输入进行敏感词检测和非法指令拦截。

- 结构化输入：避免直接拼接字符串，使用 Chat Completion 接口的 Role 机制隔离 System 和 User 内容。

- 输出清洗：对模型生成的代码或 HTML 进行 Sanitization，防止 XSS。

- 权限控制：严格限制 AI 能够调用的函数权限，遵循最小权限原则。

- 认为前端加了校验就安全了，忽略了后端校验的重要性。

- 允许 AI 直接生成并执行 JavaScript 代码。

### 向量数据库在前端有哪些应用场景？你了解它的基本原理吗？

向量数据库主要用于存储和检索高维向量，前端可用于实现本地语义搜索或长短期记忆管理。

- 原理：将文本通过 Embedding 模型转化为数值向量，通过余弦相似度等算法计算距离。

- 场景 1：本地知识库。利用 IndexedDB 配合轻量级向量库实现离线语义检索。

- 场景2：对话历史裁剪。根据当前问题检索最相关的历史对话，优化上下文长度。

- 场景 3：用户偏好匹配。将用户行为向量化，实现个性化推荐。

常见坑：

- 在前端运行大型 Embedding 模型导致性能崩溃。

- 忽略了向量维度不匹配的问题。

### React 的 useEffect 中如果涉及流式数据订阅，需要注意什么？

必须确保在组件卸载或依赖项变化时，正确关闭连接并清理资源。

- 清理函数：在 useEffect 的 return 中调用 reader.cancel() 或 abortController.abort()。

- 闭包陷阱：使用useRef存储最新的状态或使用函数式更新，避免流回调中读取到旧状态。

- 竞态处理：处理多个请求同时发出的情况，确保只有最后一个请求的结果被渲染。

- 状态同步：流式数据更新频繁，需考虑是否需要对状态更新进行批量处理。

- 忘记取消请求，导致组件销毁后依然在后台消耗流量并尝试更新状态。

- 直接在 useEffect 里写 async 函数。

### 你们项目中是如何处理长对话导致的 Token 超限问题的？

通常采用滑动窗口、摘要压缩或语义检索等策略来控制发送给模型的 Token 数量。

- 滑动窗口：只保留最近的 N 轮对话，直接丢弃更早的内容。

- 摘要压缩：将较早的对话内容通过LLM生成简短摘要，用摘要替代原文。

- 关键信息提取：提取对话中的实体和核心诉求，构建精简上下文。

- 语义检索：将历史对话存入向量库，仅检索与当前问题相关的片段。

- 简单粗暴地按字符数截断，导致 JSON 结构损坏或语义丢失。

- 忽略了 System Prompt 占用的 Token 权重。

#### 8. 手写代码：实现一个简单的 Markdown 链接解析器，提取出字符串中所有的链接和文本。

使用正则表达式匹配 [text](url) 格式。

- 正则编写：/ \( [([^]] + ) \ ] \ (([^)] + ) \ ) / g。

- 结果提取：使用 matchAll 或 exec 循环获取捕获组内容。

- 边界处理：处理嵌套括号或特殊字符转义的情况。

- 性能：对于超长文本，注意正则的回溯问题。

function parseLinks(text) {
    const regex = /\[([^\]]+)\]$([^)]+)$/g;
    const results = [];
    let match;
    while ((match = regex.exec(text)) !== null) {
    results.push({ text: match[1], url: match[2] });
    }
    return results;
}

### 如果让你从零设计一个类似 ChatGPT 的全栈架构，你会如何选型？

需要考虑实时性、可扩展性、安全性和成本控制。

- 前端：React/Next.js 负责 SSR 和流式渲染，Tailwind CSS 处理响应式布局。

- 后端：Node.js (NestJS) 或 Python (FastAPI) 处理业务逻辑，支持异步流式输出。

- 通信：SSE用于模型输出，WebSocket用于复杂交互，Redis用于对话缓存。

- 存储：PostgreSQL存储用户信息，向量数据库（如Pinecone/Milvus）存储知识库。

- 基础设施：Docker 容器化，使用 CDN 加速前端资源，接入监控系统（如 Sentry）。常见坑：

- 忽略了多端同步和离线存储的需求。

- 没有考虑 API Key 的安全存储和调用频率限制（Rate Limiting）。

### 在 AI 项目中，如何建立一套有效的自动化测试方案？

除了传统的单元测试和E2E测试，AI项目还需要针对模型输出的不确定性进行专项测试。

- 基础测试：使用 Jest/Vitest 测试 Prompt 模板生成逻辑和数据解析函数。

- E2E 测试：使用 Playwright 模拟用户交互，校验流式输出的 UI 表现。

- 模型评估（Eval）：构建测试数据集，利用“模型评测模型”（LLM-as-a-judge）对输出质量打分。

- 回归测试：记录典型的 Bad Cases，确保 Prompt 优化后不会引入旧问题。常见坑：

- 试图对LLM的输出进行完全匹配校验（这是不可能的）。

- 忽略了网络延迟和 Token 消耗对测试环境的影响。

### 如何降低大模型应用的 API 调用成本？请给出具体的优化建议。

#### 难度：★★★

成本优化应从模型选型、请求策略和缓存机制三个维度入手。

- 模型分级：简单任务（如分类、格式化）使用轻量级模型（如 GPT-4o-mini），复杂任务才调用旗舰模型。

- 缓存策略：在 Redis 中缓存常见问题的回答，或者利用语义缓存（Semantic Cache）匹配相似问题。

- Token压缩：精简Prompt，移除冗余描述，限制max\_tokens输出。

- 离线处理：对于非实时任务，采用 Batch API 批量处理，通常有 $50\%$ 的折扣。常见坑：

- 盲目追求模型能力，所有场景都用最贵的模型。

- 缺乏监控，导致某个 Bug 触发死循环调用产生巨额账单。
