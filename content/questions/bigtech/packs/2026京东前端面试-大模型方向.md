### 说一下 Promise 的状态有哪些，以及 Promise.all 和 Promise.allSettled 的区别？

Promise 有三种状态，all 和 allSettled 主要区别在于对失败状态的处理逻辑不同。

- 三种状态：Pending（进行中）、Fulfilled（已成功）、Rejected（已失败）

- Promise.all：要求所有任务都成功才返回成功，只要有一个失败就立即进入 reject

- Promise.allSettled：无论成功还是失败，都会等所有任务结束，并返回每个任务的结果数组

- 场景：all 适用于强依赖的一组请求，allSettled 适用于互不影响的并行任务常见坑：

- 忘记 Promise 状态一旦改变就不可逆

- 在 allSettled 的结果中忘记区分 status 字段

### 在 CSS 布局中，Flex 布局的 flex: 1 代表什么含义？

flex: 1 是一个简写属性，它决定了子元素如何分配父容器的剩余空间。

- 组成部分：它是flex-grow:1, flex-shrink:1, flex-basis: $0\%$ 的缩写

- flex-grow：定义放大比例，1表示占用剩余空间的1份

- flex-shrink：定义缩小比例，1表示空间不足时等比例缩小

- flex-basis：定义在分配多余空间之前的项目占据的主轴空间

### TypeScript 中的 interface 和 type 有什么区别?

两者都可以定义对象结构，但 interface 侧重于结构的声明和合并，type 侧重于类型的定义和组合。

- 扩展方式：interface 使用 extends，type 使用交叉类型 &

- 声明合并：同名interface会自动合并，同名type会报错

- 能力差异：type 可以定义基本类型别名、联合类型、元组，interface 不行

- 适用场景：定义公共 API 建议用 interface，定义复杂逻辑或联合类型用 type 常见坑：

- 试图在 type 中使用 implements 关键字

### 什么是 SSE (Server-Sent Events)? 它与 WebSocket 有什么区别?

SSE 是一种基于 HTTP 的单向推送技术，非常适合大模型这种流式输出文本的场景。

- 协议特性：基于标准 HTTP 协议，支持断线重连，数据格式默认为 text/event-stream

- 方向性：SSE是单向的（服务端到客户端），WebSocket是全双工的（双向）

- 复杂度：SSE实现简单，对代理服务器友好；WebSocket协议较重，需要独立握手

- AI应用：大模型生成回复时，前端通常通过SSE接收逐字返回的结果常见坑：

### 写一个简单的防抖（debounce）函数。

防抖是指在事件触发后延迟执行，如果在延迟时间内再次触发，则重新计时。

- 核心逻辑：利用闭包维护一个timer变量

- 关键步骤：返回一个新函数，每次调用先clearTimeout，再重新setTimeout

- 应用场景：搜索框输入联想、窗口大小调整（resize）

- 优化：支持立即执行参数（leading）

代码示例：

```javascript
1 function debounce(fn, delay) {
2    let timer = null;
3    return function(...args) {
4    if (timer) clearTimeout(timer);
5    timer = setTimeout(() => {
6    fn.apply(this, args);
7    }, delay);
8    };
9 }
```

#### 常见坑：

- 丢失了原函数的 this 指向

- 忘记传递 arguments 参数

### 算法题：给定一个字符串，找出其中不含有重复字符的最长子串的长度。

#### 难度：★★

使用滑动窗口的思想，通过两个指针维护一个不含重复字符的区间。

- 核心思路：左指针不动，右指针向右移动，并用Map记录字符出现的位置

- 遇到重复：如果右指针指向的字符已存在，则将左指针移动到重复字符位置的下一个

- 更新结果：每次移动右指针都计算当前窗口长度，取最大值

- 复杂度：时间复杂度 $O(n)$ ，空间复杂度 $O(\min(m, n))$

常见坑：

- 左指针回退问题（必须保证左指针只能向右跳）

- 字符串为空或长度为1的边界处理

### React 的 Fiber 架构解决了什么问题？它的工作原理是怎样的？

Fiber 主要是为了解决 React 在处理大量 DOM 更新时导致的页面卡顿问题，将同步更新变为可中断的异步更新。

- 核心矛盾：JS引擎与GUI渲染互斥，长耗时任务会导致丢帧

- 解决手段：引入时间切片（Time Slicing），将更新过程拆分为多个小任务

- 双缓存技术：在内存中构建 WorkInProgress Fiber 树，完成后一次性提交给真实 DOM

- 优先级调度：根据任务紧急程度（如用户输入 vs 数据请求）分配不同的优先级常见坑：

- 认为Fiber提高了代码执行速度（实际上增加了计算量，但提升了响应性）

### 手写题：实现一个带并发限制的异步调度器 Scheduler。

需要维护一个执行队列和当前正在运行的任务计数器。

- 核心逻辑：add 方法返回 Promise，并将任务包装后放入队列

- 触发执行：每当有任务完成，计数器减一，并从队列中取新任务执行

- 状态管理：确保并发数永远不超过设定的 limit

代码示例：

```javascript
class Scheduler {
    constructor(limit) {
    this.limit = limit;
    this.running = 0;
    this.queue = [];
    }
    add(fn) {
    return new Promise(resolve => {
    const task = () => fn().then(resolve).finally(() => {
    this.running--;
    this.next();
    });
    this.queue.push(task);
    this.next();
    });
    }
```

```javascript
next() {
    while (this.running < this.limit && this.queue.length) {
    this.running++;
    const task = this.queue.shift();
    task();
    }
    }
}
```

- 核心模块：可视化画布（节点编排）、资产中心（Prompt/Tool管理）、调试控制台（日志与Trace）、插件系统

- 数据流设计：采用单向数据流，画布操作实时同步至状态机，支持撤销重做（Undo/Redo）

- 性能保障：画布节点过多时采用 Canvas 渲染或分层渲染，大模型输出采用 SSE 独立通道常见坑：

- 逻辑全部耦合在画布组件中，导致难以维护

- 忽略了不同 Agent 节点间的数据 Schema 校验追问:

- 如何解决流程图中循环依赖的问题？

### 在 AI 项目中，你是如何定义和衡量 “前端用户体验” 的？有哪些具体的指标？

AI 应用的体验不仅看加载速度，更看交互的流畅度和反馈的及时性。

- 核心指标：First Token Latency（首字响应时间）、Generation Speed（生成速度 chars/s）、Request Success Rate

- 交互指标：输入框响应延迟、长文本渲染是否掉帧、自动滚动触发的准确率

- 业务指标：用户点赞/点踩比率、对话完成率、Agent任务执行成功率

- 监控手段：接入全链路埋点，记录模型返回的 trace\_id 方便排查前端渲染异常常见坑：

- 只关注首屏加载时间，忽略了模型生成过程中的卡顿

- 缺乏对模型报错后的用户行为监控

### 面对 AI 技术的快速迭代（如从单模态到多模态），前端开发者应该如何保持竞争力？

前端开发者应从“页面实现者”转型为“AI能力的整合者和交互设计者”。

- 深度掌握 AI 基础设施：熟悉 LangChain.js、Vercel AI SDK 等主流 AI 开发框架

- 探索新交互形态：研究语音交互（VAD）、视觉输入、自然语言驱动的 UI（Generative UI）

- 强化工程化能力：学习如何处理海量向量数据、如何优化长上下文的性能瓶颈

- 关注底层原理：了解Transformer基本原理、Token机制，以便更好地与算法同学沟通常见坑：

- 焦虑于工具的更替，忽略了编程基础（JS/浏览器原理）的加固

- 只会调用API，不理解AI业务背后的逻辑

### 如何在团队中推动前端代码质量的提升？有哪些具体手段？

提升代码质量需要从规范制定、工具约束和文化建设三个方面入手。

- 自动化工具：配置严苛的ESLint/Prettier规则，在CI阶段强制执行单元测试覆盖率检查

- Code Review：建立互审机制，关注逻辑健壮性、扩展性以及是否符合AI业务的最佳实践

- 文档建设：维护高质量的组件库文档和技术方案设计文档（RFC）

- 技术分享：定期进行 Case Study，分享踩坑经验，避免同类问题再次发生常见坑：

- 规范只停留在纸面上，没有强制执行力

- CR 变成走过场，只看格式不看逻辑

### 假设京东要上线一个 “AI 购物助手”，你会如何设计它的首屏加载策略以应对大流量？

针对大流量场景，核心思路是“动静分离”和“多级降级”。

- 静态资源：利用CDN全球加速，采用多域名存储资源突破浏览器并发限制

- 预加载：在用户进入页面前，通过 Link Prefetch 预加载 AI 核心逻辑包

- 接口优化：对话历史记录采用 SSR（服务端渲染）或边缘计算（Edge Computing）快速呈现

- 柔性降级：流量过大时，关闭复杂的动画效果，甚至将流式输出切换为全量输出以减少连接数常见坑：

- 所有的 AI 逻辑都打包在一个大 JS 包里

- 忽略了后端接口在高并发下的响应延迟对前端的影响

### 你对 “AI 驱动 UI 生成” （Generative UI）怎么看？它会取代前端吗？

Generative UI 是交互方式的进化，它改变了前端的生产模式，但不会取代前端。

- 核心观点：前端的工作将从“写死页面”转向“编写 UI 生成规则和约束”

- 价值所在：能够根据用户意图动态生成最合适的组件（如查机票返回机票卡片，查天气返回气象图）

- 挑战：如何保证生成 UI 的稳定性、可访问性（Accessibility）以及品牌一致性

- 结论：前端需要负责构建高质量的组件元数据（Storybook）和布局引擎，作为 AI 生成的“原材料”

常见坑：

- 观点过于极端（全盘肯定或全盘否定）

- 无法说出具体的应用场景

### 聊聊你在项目管理或跨团队协作中，是如何处理需求冲突或进度延迟的？

处理冲突的关键在于透明沟通和基于数据的决策。

- 明确优先级：使用四象限法则，优先保证核心链路（如AI对话主流程）的上线

- 风险预警：一旦发现进度可能延迟，第一时间同步给PO和相关方，并提供备选方案（如裁剪非核心功能）

- 技术复盘：分析延迟原因，是技术方案太复杂还是需求变更频繁，在下一迭代中改进

- 跨端协同：与后端/算法约定好接口契约（如 Protobuf 或 Swagger），减少联调耗时常见坑：

- 闷头写代码，直到上线前才告知进度无法完成

- 抱怨其他部门，缺乏主动解决问题的态度
